# Postly Technical Design

Postly is one TypeScript monolith on Google Cloud. Code owns the workflow, and models run only bounded tasks, so a model cannot publish or approve anything. The hybrid agent (2026-11-05, [agent.md](agent.md)) keeps this rule: its model calls are bounded tasks whose output is a list of tool calls that code checks and applies.

## Principles

- One repository, one language, and one deployable image, running as a web process and a worker process.
- A deterministic state machine manages each business, conversation, and post.
- Every model call goes through one internal layer, and its output is validated against a schema.
- Every external vendor sits behind an internal interface, so it can be replaced.
- Approval and publishing are code paths with no model involved.

## Control over prompts, models, and flow

- Prompts: each task has a versioned template, and each call records the version used.
- Models: a configuration table sets model, provider, fallback, temperature, and cost limit per task.
- Flow: states, transitions, retries, and approval points are defined in code. One business or the whole system can be paused.
- Quality: each run stores input, prompt, output, cost, and duration. Prompt or model changes run against a real Hebrew example set first.

## Operational defaults

These are defaults stored in configuration, so they can change without a code change. Times are in `business.timezone`.

| Setting | Default |
| --- | --- |
| Message burst merge | Inbound messages from one number are merged until a quiet window passes without a new one: 20 seconds by default (stage and prod), 2 seconds on dev, where the human plays the owner in the sandbox and waits on every reply. `BURST_QUIET_MS` (500 to 60000) from Terraform's `burst_quiet_ms`, set 2026-11-07. A button reply never waits; a lone text still waits the window, so an answer typed over several messages is one burst |
| Model output retries | `model_task_config.max_retries` is 2, so 3 attempts in total before routing to the console |
| Publication retries | 3 attempts in total, 5 and then 15 minutes apart, each preceded by a provider status check |
| Business week | Sunday 00:00 to Saturday 23:59; the `weekly_update` row is created at Sunday 00:00 |
| Weekly reminder | Monday 10:00, if the week is still `awaiting` |
| Week cutoff | Thursday 12:00: a week still `awaiting` or `reminded` moves to `skipped` (`WEEK_ENDED`) |
| Channel health check | Daily at 04:00 UTC (06:00 or 07:00 in Israel; WP-35) |
| Data retention after cancellation | 30 days: `data_delete_after` is `cancelled_at` plus 30 days (provisional, WP-43) |
| Data deletion | Daily at 03:00 UTC: every cancelled business past `data_delete_after` (WP-43) |
| Monthly report | 06:00 UTC on the first of each month, for the previous calendar month in `business.timezone` (WP-43) |
| Publishing tick | Every minute: publications due by `scheduled_for`, retries by the retry spacing |
| Agent limits (A4, `agent_config`, decided 2026-11-05) | 12 steps and 24 tool calls a turn, USD 0.06 a turn, USD 1.00 a business a day, USD 50 for all businesses a day, 90 seconds a turn; a limit hands the conversation off ([agent.md](agent.md#limits)) |
| Agent flows | Always on for every business in every deployed environment, with no switch (2026-11-06). The one-shot flows are a test-only composition option (`oneShotFlows`; agent.md, [Running on dev](agent.md#running-on-dev)) |
| No publishing on Shabbat and holidays | From 30 minutes before candle lighting to 30 minutes after havdalah, candle lighting at sunset minus 40 minutes in Jerusalem, 30 in Haifa and Zikhron Ya'akov, 20 elsewhere; havdalah at nightfall (sun 8.5° below the horizon); by the business's city when the city table knows its English or Hebrew name, otherwise Jerusalem |

## The agent

Decided 2026-11-05; the full design, the tools and their checks, the limits, and the human's decisions on it (A1 to A10) are in [agent.md](agent.md). In short:

- Workflow routes to the agent module (`agent.runTurn`), never the other way round; tools get the state machine events as injected callbacks ([agent.md](agent.md#module-direction)).
- The agent module runs a **turn** per trigger (a claimed burst routed by the conversation step, or a code event), holding the business's `conversation_state` row so one turn runs per business. Each step is one model-layer call of the agent's task, whose `AgentStep` output (one to four tool calls and a confidence) is Zod-validated, retried and recorded like every task; `model_run.agent_turn_id` ties the calls to the turn.
- Each tool call is checked (allowed for this agent and state, its schema, its code checks: verbatim quotes, the fact check, the plan checks, the design ranges, the badge rules) and applied through the owning module in its role and transaction. A refusal changes nothing and goes back to the agent.
- Messages the agent proposes (`ask_owner`, `request_photo`) are sent by messaging only inside the 24-hour window; drafts are sent with their buttons by the drafts code, exactly as below. Approval, times, scheduling, rendering and publishing are untouched.
- Code evaluates each agent's "done" rule after each step and applies the state machine event (state-machines.md, [Agent-driven steps](state-machines.md#agent-driven-steps)).
- Limits (steps, tool calls, cost per turn, per business per day and in total, time, repeated questions, low confidence, refusals) end the turn with a hand-off: the handoff flag, an `agent_limit` or `handoff` console item with the turn id, and a fixed line to the owner.
- Tests never call a real model: the scripted agent drives every unit, db and e2e test, and the real-Gemini eval is a manual, opt-in script (agent.md, [Testing](agent.md#testing-without-paying-for-a-model)).

The flows below describe the fixed (one-shot) path, which no deployed environment runs any more: the agents always run, and the parts they take over are named in each flow's agent note. The one-shot path stays in the code for the tests that drive it until A9's cleanup.

## Onboarding flow

Built in WP-30 (2026-11-03); the copy is provisional (H6) and queued for the human. The workflow module runs the [onboarding machine](state-machines.md#onboarding); each step uses the module that owns it.

- **Inbound media.** Messaging downloads every voice note and image through `getMedia`, stores the file, records a `media_asset` row (`voice` or `photo`, source `owner`), and passes the asset ids with the burst. Voice notes are transcribed with the `transcription` task before anything reads the text.
- **Agent note.** With the onboarding agent (always on, WP-92), the profile questions, the brand assets and profile corrections are the agent's, and code applies `PROFILE_FIELDS_COMPLETE`, `BRAND_ASSETS_DONE` and `PROFILE_CORRECTED` when the agent's turn ends done ([agent.md](agent.md#the-onboarding-agent-in-the-flow-wp-92)); the intro (now in the persona's voice, feminine), style samples, profile summary, channel connection and activation stay as below.
- **Profile questions.** One or two topics per message, in a fixed order: name, field and products; location, hours, and pickup or delivery; audience and differentiator; channels and Shabbat publishing. Each answer goes to `profile_extraction` with the fields asked, and the fields found merge into the `BusinessProfileDraft` in `business.profile`. A question whose required fields stay empty is asked again, up to three times in all, and then the conversation is handed off to a person.
- **Brand assets.** The agent asks for a logo, then for photos of the business; the owner can skip each. The first image after the logo question is the logo (`brand.logoAssetId`).
- **Style samples.** The design module renders one sample post per style from the owner's first photo (or a bundled sample photo when there is none), with the business name and logo, and messaging sends each with its style name. The owner answers with a style name or number.
- **Profile review.** A short summary; the owner approves by text from the approver number, or writes a correction, which goes through `profile_extraction` and resends the summary.
- **Channel connection.** The publishing module creates a `pending` `channel_connection` per chosen network and sends the provider link. The owner writes when done; the module reads the provider status and applies `CONNECTED`, then the test: the provider's `testSchedule` confirms a post can be scheduled on the account without publishing anything (`TEST_PASSED`, or `TEST_FAILED` and the link again; WP-34), and the business becomes `active`.
- **Bursts are durable (review queue items 13, 14 and 24).** No burst waits in process memory. Every inbound message is stored in `message` with `processed_at` null at once, and the burst is whatever is stored for that business and sender and not yet processed. Storing a message requests a wake-up for that business and sender one quiet window later: in deployed environments a pg-boss job `inbound-burst` on a queue with the `short` policy, `singletonKey` business id and sender, `startAfter` the quiet window (Operational defaults), so at most one such job waits per sender however many web instances received the burst. The job runs in the web process on whichever instance pg-boss gives it to. When it runs, messaging claims the sender's unprocessed messages in one transaction (`SELECT ... FOR UPDATE` on the sender's unprocessed rows, so a second claimer waits for the first to commit, then `claimed_at` set). While an earlier message of the sender is claimed by someone else and not processed, it claims nothing and requests another wake-up, so bursts are handed over in order. When the newest is younger than the quiet window it claims nothing and requests another wake-up for the newest message plus the quiet window; otherwise it claims the first burst (texts, images and voice notes in order; a button reply always alone), hands it to the workflow, then sets `processed_at`, and repeats for the next burst. A claim is a lease: a claim older than 5 minutes whose message is still unprocessed (the process died while handling it) can be claimed again, and a handler that throws clears its claim at once, so the sweep retries it. A button reply is handed over at once, in the request that stored it, after the sender's earlier messages (the same claim, without waiting for the quiet window). The sweep stays as the backstop for a lost wake-up: at startup and then every quiet window it runs the same claim for every business and sender with an unprocessed inbound message older than the quiet window. Since every handover goes through the claim, two web instances, the job and the sweep never hand the same message over twice. Locally and in tests the wake-up is an in-process timer with the same claim behind it.

## Weekly update flow

Built in WP-31 (2026-11-03); the copy is provisional (H6) and queued for the human. The workflow module runs the [weekly update machine](state-machines.md#weekly-update) and the conversation's first step; the content module owns the code checks on the model output.

- **Agent note.** With the weekly agent on, recognizing the update and `UPDATE_RECEIVED` stay as below; fact extraction and planning become the weekly agent's `record_fact`, its questions about missing details (`QUESTION_ASKED`, `ANSWER_RECEIVED`), `request_photo`, and `plan_posts`, whose checks are the planning checks below plus an owner quote for any departure from the profile. A hand-off or limit before a plan applies `EXTRACTION_FAILED`.
- **Week rows.** A scheduler tick (`WeeklyUpdates.tick(now)`) runs every hour. It finds active businesses with `withSystem('scheduler')`, then per business, in the business's timezone, it does what is due: from Sunday 00:00 it creates the week's `weekly_update` row (`awaiting`; an existing row is kept); from Monday 10:00, for a week still `awaiting`, it applies `REMINDER_SENT` first and then sends the reminder, so a crash or a second tick never sends it twice (at most once: a failed send is logged and not retried; WP-32 fix); from Thursday 12:00 it applies `WEEK_ENDED` to a week still `awaiting` or `reminded` (a week that was never reminded, for example because the business was activated after Monday 10:00, closes at the cutoff too; WP-32 fix). Each step is idempotent, so a late or repeated tick does no harm.
- **Reminder template.** `weekly_reminder`, in the business's first language, with one variable, `businessName`. It goes out with `sendTemplate`, because the 24-hour window is usually closed. The template text is submitted to WhatsApp for approval with the H6 copy.
- **Recognizing an update.** A burst from the approver number while the conversation is `idle` is an update when it holds a photo or a voice note, or when `intent_detection` on its text returns `weekly_update`. Other intents are left to the packages that handle them. Voice notes are transcribed first, as in onboarding.
- **Which week.** The update goes to the current week when it is `awaiting` or `reminded` (`UPDATE_RECEIVED`). A missing row (a business activated mid-week) is created first. **Late update:** when the current week is already `skipped` (after the Thursday cutoff), the update is not lost: it opens next week's row early and counts as next week's update, and the owner is told the posts go out next week. Decided 2026-11-03 by WP-31 and queued for the human.
- **A second update in the same week** (decided 2026-11-03 by WP-32, queued for the human). An update is never dropped without a reply. While the conversation is `processing_update` or `awaiting_answer` (the agent is still preparing the last update's drafts), the owner is told the agent is still working on the previous update and to send the new details as a change once the drafts arrive; nothing is applied. While it is `reviewing_drafts`, the update is a change request on the open drafts (state-machines.md, Conversation). While it is `idle` and the current week is already `received`, `needs_review`, or `planned`, the update counts as next week's update (next week's row is opened early), and the owner is told this week already has its update (not that the week closed); if next week's row is not open either, the owner is told an update for next week is already in.
- **Stored on the row.** `original_text` (the typed text), `transcript` (the voice transcripts joined), `media_asset_ids` (the photos), `received_at`, and after extraction `extracted_facts`.
- **Fact extraction.** `fact_extraction` gets the text, the transcript, and a short profile summary. Code then checks that every `sourceQuote` appears word for word (whitespace runs count as one space) in the text or the transcript, and that a `testimonial` quote appears in the typed text. A failed check counts as a failed attempt in the model layer (`RunOptions.check`), so it retries like a schema failure and then lands in the console.
- **Weekly planning.** `weekly_planning` gets the facts, `postsPerWeek`, the profile's content types and formats, and the photos. Code checks that there are exactly `postsPerWeek` posts, that every `factIds` entry is an extracted fact, every format is in the profile, and every `mediaAssetIds` entry is a photo of this update. The same retry rule applies.
- **Plan stored.** `FACTS_EXTRACTED` saves `extracted_facts` and inserts one `post` per planned post (`planned`, `position` in plan order, `format`, `plan`) in the same transaction; then the conversation moves from `idle` to `processing_update` (`UPDATE_RECEIVED`) and the owner gets a short acknowledgment. Missing details stay in `extracted_facts.missingDetails`; drafting asks about them (WP-32).
- **Failure.** When extraction or planning fails every attempt, `EXTRACTION_FAILED` moves the week to `needs_review` (the console item already exists), the conversation stays `idle`, and the owner is told the team is looking at it. Any other error while extracting, planning, or storing the plan also applies `EXTRACTION_FAILED` and opens an `extraction_failed` console item, so a week never stays `received` unseen (WP-32 fix). A model failure before the update is recognized (transcription or intent) hands the conversation to a person, as in onboarding, and the owner gets a neutral line that a person will answer, never "update received" (WP-32 fix).

## Drafts flow

Built in WP-32 (2026-11-03); the copy and the `caption_writing` version-2 prompt are provisional (H6, H7) and queued for the human. The workflow module runs the [post machine](state-machines.md#post) and the conversation from `processing_update` to `reviewing_drafts`; the content module owns the fact check and the content hash; the design module renders. Approval itself is WP-33.

- **Agent note.** With the drafts agent on, the caption, the several-photos question, the overlay text (now the design's `title`, fact-checked), the photo edits, the optional badge, the carousel order and changes are the drafts agent's `create_draft`, `ask_owner`, `plan_posts` (revise) and `apply_change`. The fact check, the version and hash, invalidation, rendering and sending with buttons stay exactly as below; the version also stores its `design_spec`. Free text that is not a change still only resends the drafts.
- **When.** Right after the plan is stored (`FACTS_EXTRACTED`, conversation `processing_update`), the week's posts are drafted one by one in `position` order, in the same handler (WP-44 may move this to a job). When every post is sent, failed, or waiting for an answer, `DRAFTS_SENT` moves the conversation to `reviewing_drafts`. When no draft could be sent at all, the conversation is handed off to a person (the console items already exist) and the owner is told the team is looking at it. Any other error while drafting (not a model failure, for example a send that fails) opens a `draft_failed` console item for the week and hands the conversation to a person, so it never waits in `processing_update` answering every message with "still working" (review of PR #43).
- **Several photos.** A post planned as `single` with more than one photo is not drafted yet: `DRAFT_STARTED`, then `DETAIL_MISSING` (`awaiting_clarification`), and the conversation asks one question (`QUESTION_ASKED`, open question `photo_choice` with the post id): 1 for a carousel, 2 for one photo, 3 for a post per photo. Choices are answered by text, because buttons carry approval payloads only. Code reads the answer from the digit or the words (קרוסלה; אחת; כל תמונה or נפרד); any other answer is asked again, up to three times in all, and then the conversation is handed off. On a valid answer the conversation applies `ANSWER_RECEIVED` and the post `DETAIL_PROVIDED`. Carousel sets the post's `format` to `carousel` (the owner's choice wins over the profile's formats); one photo keeps the first photo; a post per photo keeps the first photo on this post and inserts a new `planned` post for each other photo after the week's last position, so the week can hold more posts than `postsPerWeek`.
- **Caption.** `caption_writing` gets the plan, the facts the plan names, a short business context, the active preference rules, the post's networks (the profile's channels, or the networks of the current version after a channel change), the languages, the tone, the fixed hashtags, and on a redraft the change instructions (`changes`). Code runs the fact check below as `RunOptions.check`, so a mismatch is a failed attempt: the model retries, and when every attempt fails the post moves to `needs_review` (`DRAFT_FAILED`; the model layer's console item exists) and nothing is sent for it. The optional `fact_check` model task is not used in Phase 1.
- **Fact check (code).** Every `usedFactIds` entry must be a fact the plan named. Then each detail in every caption's text and hashtags is matched against sources of its own kind (review of PR #43): a phone (by its digits, `+972` read as `0`) against a phone fact or the profile's contact details; a price (a number next to ₪, ש"ח or שקל) against a price fact or a number shown as a price in a source; a discount (a number with %) against a discount fact or a percentage in a source; a time (`H:MM`) against a time fact or a time in a source such as the hours; a date (`D/M` or `D.M`) against a date fact or a date in a source; a weekday name (יום ראשון to שבת) against the sources. Any other number (a house number, a quantity) may match any number in the sources. So "12 ₪" fails even when the address has 12. The sources are the used facts (value and quote) and the profile's address, city, hours, contact details, and differentiator. A testimonial is written only from a fact the owner typed (checked at extraction). The used facts are stored on the version as `fact_sources`.
- **Hebrew details in words (T8, 2026-11-04).** Before matching, code reads the written Hebrew forms of these details in both the caption and the sources, so the same rules apply to them:
  - a number in words (אחד to תשעים ותשעה, מאה, מאתיים, X מאות, אלף, אלפיים, X אלפים, with ו between parts and an optional ו, כ, ב, ל, מ or ה prefix, or ו with one of the others) counts only next to a factual marker: before ₪, ש"ח or שקל (a price), before אחוז (a discount), or before a month (a date). A number word with no marker ("פעם אחת", "אחד הטעמים") is not a detail, so ordinary prose is never blocked;
  - a date is `D/M`, `D.M`, or a day and a month name (`15 בנובמבר`, `חמישה עשר בנובמבר`, `הראשון בדצמבר`, with an optional year); dates compare as day and month, so `15.11`, `15/11` and `15 בנובמבר` are the same date, and a caption date with no year matches a source date with one;
  - a time is `H:MM` or `בשעה` with a number in digits or words, with an optional וחצי or ורבע and an optional part of day (בבוקר, בצהריים, אחה"צ, בערב, בלילה, which adds 12 from noon on); `08:00` and `8:00` are the same time, and a bare hour with no part of day ("בשעה שמונה") matches either 8:00 or 20:00;
  - a weekday is יום ראשון to שבת, יום א׳ to יום ו׳, or the forms בשלישי, ברביעי, בחמישי, בשישי, בשבת (בשני and בראשון are left out, since they also mean "in two" and the city ראשון לציון); a range of days in a source, such as א׳-ה׳ or ראשון עד חמישי, vouches for every day in it;
  - `20 אחוז` is a discount like `20%`; `100%` (and מאה אחוז) is emphasis and is not checked, unless הנחה follows it or comes right before it ("100% הנחה", "הנחה של 100%"), where it is a discount like any other.
  A price, discount, or date written in words with no marker, and a time written without בשעה ("בשמונה בערב"), are not read; the owner still sees every caption before approving it. Asking the `caption_writing` prompt to write factual details in digits is a possible follow-up (a customer-facing prompt change, H7).
- **Rendering.** The design module renders the post in the business's style with the plan's photos (all of them for a carousel, the first for a single post). A post with no photo uses the business's latest owner photo from the media library, or the bundled sample photo when there is none. The overlay text is the plan's `topic`; the logo and brand colors come from the profile; the networks are the post's networks. Every rendered file is stored as a `media_asset` (`rendered`, source `render`) by the design role, and `rendered_media` maps each network to its asset ids in slide order. A render error is handled like a failed draft: `DRAFT_FAILED` and a `draft_failed` console item.
- **Version.** A new `post_version` (the next `version_number`) holds the captions, `rendered_media`, `fact_sources`, `fact_check_passed` (always true: a draft that fails the check is never written), and `content_hash`: SHA-256 (lowercase hex) of the canonical JSON (keys sorted) of `{ format, captions, renderedMedia }`. `post.current_version_id` points at it, in the same transaction.
- **Sending.** The Approve button carries the hash of every network's caption and render, so the owner is shown all of them before the buttons (review of PR #43). Networks go in a fixed order, Instagram then Facebook. Each render of a network after the first that differs from the first's (compared by the files' SHA-256, so an identical render is shown once) is sent first as an image labelled with its network (`sendText` with `mediaUrl`); for a carousel, each slide of the first network is sent too. Then one `sendButtons` message carries the first network's cover image, the captions (shown once when they are identical, otherwise each under its network's name), and a "details to check" line listing the factual details (PRD, Content safeguards), with two buttons, אישור and שינוי. Each button id is `<action>:<postId>:<versionId>:<versionHash>` (T15: bound to the exact version row), which the messaging adapter maps to `ApprovalButtonPayload`. Then `DRAFT_READY` moves the post to `awaiting_approval`.
- **While drafts are open** (`reviewing_drafts`). An Approve tap goes to the [approval flow](#approval-flow) (WP-33). A Change tap asks what to change and remembers the post (open question `change_request` with the post id). A text goes to `intent_detection` (step `reviewing_drafts`, drafts open): a `change_request` or a `weekly_update` is a change request on the post the owner tapped Change on, or else on the only open draft; with several open drafts and no tap, the owner is asked to tap Change on the draft they mean. Any other text (such as "sounds good") resends every open draft with its buttons, unchanged. A post in `awaiting_approval`, `approved` or `scheduled` takes a change here; a change to an `approved` or `scheduled` post invalidates its approval first (see the approval flow). A Change tap does not compare its `versionHash` with the current version: a change always applies to the current version, so an old draft's Change button is harmless. Approve taps never follow this pattern (review of PR #43, item 3). A button tap while the several-photos question is open is not an answer: the question is asked again without counting an attempt (item 4).
- **A change.** `change_interpretation` reads the text with the current captions and plan. The change is saved at once as a preference rule (PRD, Context that updates automatically): the model's `rule` when it gives one, otherwise the instructions joined, with the scope of the first change (`caption`; `design` for design and media; `schedule`; `general` for channels). The rule's `source_message_id` is the owner's message and `source_post_version_id` the version it changed. A `channels` change that names only Instagram or only Facebook narrows the post's networks to that one. Then the conversation applies `CHANGE_REQUESTED` (to `processing_update`), the post `CHANGE_REQUESTED` (to `drafting`), and the post is drafted again with the change instructions and every active rule: a new version, a new hash, and new buttons; `DRAFTS_SENT` returns the conversation to `reviewing_drafts`.
- **Still open.** Missing details from extraction (`extracted_facts.missingDetails`) are not asked about yet: the caption may not invent them, and the fact check blocks any number without a source. Asking one focused question about them is a follow-up.

## Approval flow

Built in WP-33 (2026-11-04), queued for the human (approval code). The approval service (`createApprovals` in the workflow module, running as the `approval` role) implements `ApprovalService` from [contracts.md](contracts.md#approval-and-publishing), behind the [approval guard](state-machines.md#approval-guard). No model is involved.

- **Routing.** Messaging hands every button reply over as a burst of its own. In an active business, an Approve tap from any conversation step goes to the approval service before any other flow; a Change tap goes to drafts. Messages from a number that is no business's approver never reach a business (technical-design.md, Failure handling: an unknown number becomes a console item), so a stranger's tap approves nothing.
- **Checks, in order.** A message that is not a button reply, or a button whose action is not `approve`, is `not_a_button`. A sender other than `business.approver_phone` is `not_approver`. A business that is not `active` (onboarding, paused, cancelled) approves nothing: `wrong_state`. A business in handoff is `handoff`. Then the message is recorded (the stored row when messaging received it, otherwise messaging stores it with `processed_at` set), and one transaction locks the post row (`for update`) and checks: no such post for this business (RLS hides another business's post) is `unknown_post`; a post not in `awaiting_approval` is `wrong_state`; a hash that is not the hash of `post.current_version_id` is `stale_version` (including a hash of no version and another post's hash). So a stale tap on a post that is no longer awaiting approval is `wrong_state`; both get the same reply. The transaction is the workflow's `apply` for `APPROVED`, run as the `approval` role (an event may name a role other than the machine's default, when that role may update the status column): `not_found` is `unknown_post`, a transition not allowed from the current state is `wrong_state`, and the hash check is the event's guard. Only then the `approval` row is inserted (version id, hash, approver phone, message id, time) and the post moves to `approved`, in the same transaction. A draft is sent before `DRAFT_READY` is applied, so if that event is refused the owner holds buttons for a post that is not `awaiting_approval`; the state check refuses them (`wrong_state`; review of PR #43, item 2). An approval already tied to this message is `duplicate`. That read runs just before the transaction, outside the post lock, on purpose (review of PR #48): a message already handled must say `duplicate`, not the `wrong_state` its own approval caused, and the lock is not what keeps it safe. A second handling that races past the read either waits on the post lock and then fails the state check (`wrong_state`, nothing written) or fails the unique `approval.message_id` on insert, which rolls back its transaction and is reported as `duplicate`. Either way one message approves at most once.
- **Replies.** An approval gets a short confirmation. A `stale_version` or `wrong_state` tap gets a line that the draft is no longer current, and the open drafts are sent again with their buttons. `not_approver` and `handoff` get no reply. When every draft is resolved, the time proposal follows ([Scheduling and publishing flow](#scheduling-and-publishing-flow)).
- **Invalidation.** Before any new `post_version` is written, and before `CHANGE_REQUESTED` is applied to an `approved` or `scheduled` post, every approval of the post that is not invalidated gets `invalidated_at` (approval role) and its `scheduled` or `retry_pending` publications are cancelled (publishing role). Invalidation comes first, so a failure after it leaves a post that cannot publish, never one that publishes stale content; the publishing guard checks the approval again anyway. When the change is then refused, the post stays `approved` with no valid approval, so a `draft_failed` console item (reason `change refused after approval was invalidated`) tells the team (review of PR #48).
- **Scheduling.** Scheduling an approved post (the owner confirming times) creates one `scheduled` publication for each network of the approved version (the keys of its captions, so a post narrowed to Instagram publishes only there), each on that network's `verified` connection, from the post's valid approval, copies the approved hash, and applies `SCHEDULED`, in one publishing-role transaction. If a network of the approved version has no verified connection, nothing is scheduled and the call fails (review of PR #48); the schedule confirmation turns that into an owner message and a console item ([Scheduling and publishing flow](#scheduling-and-publishing-flow)).

## Scheduling and publishing flow

Built in WP-34 (2026-11-04), queued for the human (publishing code, provisional Hebrew copy and template text, the channel test contract). The publishing module owns the time proposals, the publications and the publishing job; the workflow module runs the conversation. No model is involved.

- **How times are worded** (agent.md, [Time proposals](agent.md#time-proposals)). Each proposed time is labelled as the owner's usual slot when it comes from the profile's days and hours, and as a default slot otherwise; no message claims the time is when followers are most active until WP-72.
- **Time proposals** (`proposeTimes`, pure code). One time per approved post, in `position` order, each on a different day. Days are the profile's `schedule.days`, or Sunday to Thursday when empty; the hour is the profile's `schedule.hours` in turn, or 10:00 when empty, in `business.timezone`. A time is at least one hour from now. Unless `publishOnShabbatAndHolidays`, a time inside the no-publishing window (Configuration defaults: Shabbat and Israeli yom tov from 30 minutes before candle lighting to 30 minutes after havdalah, by `jewish-calendar.ts`, at the profile's city when its English or Hebrew name is in the city table, otherwise Jerusalem; yom tov days are Rosh Hashana (two days), Yom Kippur, Sukkot I, Shemini Atzeret, Pesach I and VII, and Shavuot, with neighbouring rest days merged into one window) moves to the next allowed day. The search looks 21 days ahead.
- **Proposing.** After each approval, when the conversation is in `reviewing_drafts` and every post of the week is `approved` or `cancelled` with at least one `approved`, the conversation applies `ALL_DRAFTS_RESOLVED` (to `confirming_schedule`) with the open question `schedule_confirmation`, whose `proposals` hold each post id and its proposed time, and the owner gets one message listing each post's topic and time and how to confirm.
- **Confirming.** In `confirming_schedule`, a short confirming text (`SCHEDULE_CONFIRM_WORDS`) creates the publications of every proposed post that is still `approved`, at its proposed time ([scheduling](#approval-flow)), then applies `SCHEDULE_CONFIRMED` (to `idle`), and the owner gets a confirmation listing the times. This text accepts times only; a post is approved only by its button. A post whose network has no verified connection is not scheduled: the owner is told which channel needs reconnecting, a `channel_disconnected` console item opens, and the conversation is handed to a person. Any other text in `confirming_schedule` is a schedule change: in Phase 1 the conversation is handed to a person (a `handoff` console item with the owner's text) and the owner is told someone will set the times; reading requested times from text is a follow-up. An Approve tap keeps its usual path. A Change tap reopens the drafts: `CHANGE_REQUESTED` (to `processing_update`, dropping the proposal) and `DRAFTS_SENT` (back to `reviewing_drafts`), then the drafts flow takes the tap, and once every draft is resolved again the times are proposed again. Any other message here is a schedule change. A change to a scheduled post after the times were confirmed (conversation `idle`) is not routed to drafts yet; that is a follow-up.
- **The publishing job** (`createPublishingJob`, publishing role) implements `PublishingJob` from [contracts.md](contracts.md#approval-and-publishing). `runPublication` runs the [publishing guard](state-machines.md#publishing-guard) in one transaction that locks the publication, and on a pass applies `STARTED` (`attempts` + 1) and, for the post's first publication, the post's `PUBLISHING_STARTED`. The handoff check comes from the workflow module (the publishing role cannot read `conversation_state`). Then, outside the transaction and inside one error handler (WP-35): the job loads the approved version and applies the post's `PUBLISHING_STARTED`; a publication that already holds a `provider_post_id` asks `getPublicationStatus` first, and `scheduled` or `published` there ends as `already_published` with no new `publish`, while `failed` there counts as a failed attempt and clears the stored id; otherwise `publish` gets the publication id as idempotency key, the channel's account, the approved version's caption for that network (the text, then the hashtags on a new line), the version's rendered media for that network as URLs, its format, and `scheduled_for`. The provider id is stored in its own write as soon as `publish` returns, before `SUCCEEDED`, so a crash or error after that point leaves a retry that checks the provider first (WP-35).
- **Results.** Success applies `SUCCEEDED`: the provider holds the post and it is never sent again. `published_at` is set only once `getPublicationStatus` reports `published` (WP-35). Any error in the run, from the provider or not (loading the version, recording the result), applies `ATTEMPT_FAILED` (`retry_pending`, `last_error`) while attempts are below 3, otherwise `ATTEMPTS_EXHAUSTED` (`failed`) with a `publication_failed` console item; an error that did not come from the provider opens a `publication_failed` item at its first attempt, so the team sees it at once (one open item per publication; later failures while it is open add none). If even recording the failure fails, the publication stays `in_progress`, and the tick's sweep later records it as a failed attempt (`attempt interrupted`): every error path ends in `retry_pending` or `failed` with a console item. When every publication of the post is `published`, `failed` or `cancelled`, and the provider reports every `published` one as live (status `published`, which sets `published_at`), the post applies `ALL_PUBLISHED`, `PARTIALLY_PUBLISHED` or `ALL_FAILED`, and the owner gets one template (networks always listed Instagram first, then Facebook): `publication_confirmation` (the topic and the networks) when all went live, otherwise `publication_failed` (the topic and the failed networks), which the team sees as the console item. Templates, because the 24-hour window has usually closed.
- **When it runs.** The worker's `publishing-tick` job runs every minute (`Publishing.tick(now)`): it finds due rows with `withSystem('scheduler')` (`scheduled` once `scheduled_for` passed; `retry_pending` 5 minutes after the first attempt and 15 after the second, from `updated_at`) and runs each one. It also sweeps `in_progress` rows not updated for 10 minutes (a run that crashed) into a failed attempt with a console item, and asks again about posts whose `published` publications are not confirmed live yet, so the owner's confirmation goes out once the provider reports them `published`. A failure of one publication is logged and does not stop the others.

## Failure handling required in Phase 1

- The 24-hour window closes mid-flow: send an approved template, or wait for the owner.
- A draft gets no response: keep it unapproved and do not publish it.
- Approval arrives after the proposed time: propose a new time.
- One channel fails: record per-channel status, retry safely, and notify the owner and team.
- A channel disconnects: daily health check, then notify the owner with a template.
- A message comes from an unknown number: never accept approval or changes from it.
- A model output fails validation: retry within a limit, then route to the console.

How each case is handled (WP-35, 2026-11-04; each has an end-to-end test):

- **Closed window.** A free-form send outside the window fails with `WindowClosedError` (contracts.md, MessagingProvider). When drafts are ready but the window has closed (for example a week drafted again from the console a day after the owner last wrote), each draft still becomes `awaiting_approval`, `DRAFTS_SENT` moves the conversation to `reviewing_drafts`, the open question becomes `drafts_waiting`, and the owner gets one template, `drafts_ready` (variable `businessName`), asking them to write. Nothing else is sent. The owner's next message, whatever it says, is answered with a short line and every open draft with its buttons, and the question is cleared; it is never read as an approval or a change.
- **No response.** A draft nobody answers stays `awaiting_approval`, with no reminder about drafts in Phase 1. No time is proposed, no publication exists, and the ticks (weekly and publishing) never publish it, however much time passes.
- **Late approval.** Times are proposed only after the last approval, so "late" means the owner confirms after a proposed time has passed. Then nothing is scheduled: new times are proposed for the posts still `approved` (the same rules, from now), the open question keeps `schedule_confirmation` with the new proposals (`attempts` + 1), the owner is told the earlier time has passed, and the conversation stays in `confirming_schedule`. A post is never scheduled for a time in the past.
- **One channel fails.** Per-channel publications, retries and the owner's `publication_failed` template, as in the [scheduling and publishing flow](#scheduling-and-publishing-flow).
- **Channel disconnect.** The worker's `channel-health-check` job runs daily at 04:00 UTC (06:00 Israel time in winter, 07:00 in summer; pg-boss cron runs in UTC). For every active business it asks `getConnectionStatus` about each `verified` connection. One that is still `connected` with the same account gets `last_health_check_at`. Any other answer applies `HEALTH_CHECK_FAILED` (to `disconnected`), opens a `channel_disconnected` console item (network and provider status), and sends the owner the `channel_disconnected` template (variable `networks`); the team then sends a new link (`RECONNECT_REQUESTED`). A provider error for one business is logged and does not stop the others. Publications already scheduled on that channel are not cancelled: the publishing job tries them and, if the channel is still gone, they fail as in "one channel fails".
- **Unknown number.** Messages from a number that is no business's approver are stored without a business and become an `unknown_number` console item (WP-22). No reply goes out, and no button (Approve or Change) or text from it reaches any business.
- **Provider failure of a known post.** When the publication already holds a `provider_post_id` and `getPublicationStatus` reports it `failed`, a retry cannot help: the idempotency key is the publication id, so `publish` would return the same failed post (review of PR #52, item a). The attempt applies `ATTEMPTS_EXHAUSTED` (`failed`) whatever the attempt count, keeps `provider_post_id`, and opens a `publication_failed` console item. A console retry of it ends the same way; the team republishes it by hand.
- **A post the provider drops after accepting it.** A publication that is `published` (the provider held it) and that the provider later reports `failed` gets `last_error` and counts as failed for its post: the post applies `PARTIALLY_PUBLISHED` or `ALL_FAILED` and the owner gets `publication_failed`, so the post never stays in `publishing` (review of PR #52, item b). `publication_failed` console items are idempotent: one is inserted only when no open one exists for the same publication, checked while the publication row is locked, so sibling publications finishing in parallel do not add duplicates.
- **Failed model validation.** The model layer retries within the task's limit and then opens a `model_validation_failed` console item (WP-21); each flow then hands the conversation to a person or marks the draft failed, as its section says.

## Billing

T1, 2026-11-04. There is no trial: the owner pays at once, at ILS 300 a month (PRD, Payment).

- **Price.** One setting, the `plan_price` table (database-schema.md): append-only, so every change is kept with who made it; the current price is the newest row. The team changes it from the console. Billing reads it each time it creates a link and passes it to `createPaymentLink`.
- **Payment link in onboarding.** When onboarding activates the business (`ONBOARDING_COMPLETED`), the owner gets the activation message and then billing's `sendPaymentLink`: the provider link is created with the current price, the `subscription` row is stored `pending`, and the link goes to the approver in WhatsApp (the owner just wrote, so the window is open). A send that fails is logged and opens a `payment_link_failed` console item (details: the error); the business stays active and the team resends the link. Without a payment provider wired, no link is sent.
- **Status.** The provider's callback moves the row (`pending` to `active` on payment; state-machines.md, Subscription). The owner is told on every change.
- **Billing hold (T16, 2026-11-05).** An unpaid subscription pauses publishing after a grace period; nothing is cancelled or deleted.
  - *Grace start.* `subscription.grace_started_at` is set when the row is first stored `pending` (the first payment link; a resent link does not restart it) and when the row becomes `past_due` (`PAYMENT_FAILED`). `PAYMENT_SUCCEEDED` clears it, with `reminders_sent` and `held_at`.
  - *The daily tick* (`billing-hold`, 05:00 UTC, worker) takes every `active` business (scheduler role) and, under the billing role, its subscription when it is `pending` or `past_due`. Day *n* is the whole days since `grace_started_at`. On days 1, 3 and 6 it sends one reminder template (`reminders_sent` counts them; a missed tick sends only the latest due reminder, never two at once): `payment_reminder` with a fresh payment link for `pending` (as `sendPaymentLink` does, which replaces `provider_customer_id`), `payment_failed` for `past_due` (no new link, which would detach the provider subscription; the owner replies and the team helps). From day 7, when `held_at` is empty, it sets `held_at`, applies the business `PAUSE` (source `system`) and sends `publishing_on_hold`. A business that is not `active` (team-paused, onboarding, cancelled) is skipped, so the hold never overrides or doubles a team pause.
  - *The pause* is the existing business pause, not a new path: the publishing job defers every publication of a `paused` business (`business_pause`) and re-checks right before the provider call; approvals answer `wrong_state`, as for a team pause. Posts, versions, approvals, publications and data are untouched.
  - *Payment.* When the callback applies `PAYMENT_SUCCEEDED`, billing clears the hold columns, tells the owner (`BILLING_COPY.active`), and, only if `held_at` was set, applies the business `RESUME`. Deferred publications then publish on the next publishing tick, late if their time passed. A `RESUME` refused by its guard (no `verified` channel) is logged and leaves the business to the team.
- Local runs and tests use the payment simulator; the vendor (PayPlus or Grow) is still open.

## Cancellation, data deletion and the monthly report

WP-43, 2026-11-04. Each has an end-to-end test.

- **Cancellation.** A business is cancelled by the team from the console (`POST /api/businesses/:id/cancel` with the business name typed as confirmation, `{ confirmName }`; a missing or different name is refused with 400 and nothing runs (security.md D2); after the owner asks; the owner's `cancel_request` intent is handled by a person) or when the payment provider reports the subscription `cancelled` (billing's webhook). Cancellation runs in this order, and each step is idempotent, so running it again finishes a cancellation that stopped half way:
  1. The business applies `CANCEL` (to `cancelled`), whose guard sets `cancelled_at` and `data_delete_after` (`cancelled_at` plus the retention period). A business already `cancelled` keeps its dates.
  2. Every channel connection that is not `revoked` is disconnected at the provider (`disconnectAccount`, when it has a `provider_account_id`) and applies `REVOKED` at once. A provider error does not stop the revoke: the channel is `revoked` in Postly (nothing publishes on it), and a `channel_disconnected` console item (reason `cancellation`) tells the team to finish the disconnect at the provider.
  3. Every `scheduled` or `retry_pending` publication applies `CANCELLED`, and every post that can still be cancelled (state-machines.md, Post) applies `CANCELLED`. The publishing guard already refuses a business that is not `active`.
  4. The subscription, when it has a `provider_subscription_id` and is not `cancelled`, is cancelled at the payment provider (`cancelSubscription`) and set `cancelled`.
  5. The owner gets the `subscription_cancelled` template (variable `deleteAfter`, the deletion date), because the window may be closed. It is sent once: a run checks for an outbound message of that template first, so a cancellation that stopped at an earlier step sends it when it is run again. The payment provider is called outside any transaction (its cancel is idempotent), and the stored status is set after it under the row lock.
- **Data deletion.** The worker's `data-deletion` job runs daily. It finds with `withSystem('scheduler')` every business that is `cancelled` with `data_delete_after` in the past, and for each, as the `deletion` role inside that business's context: reads the storage paths of its `media_asset` rows, then deletes the `business` row with `status = cancelled` and `data_delete_after <= now` in the delete's own condition, so a business that is not due is never deleted even if the scheduler's read was stale. Every business-owned table references `business` with `on delete cascade`, so that one delete removes all the business's rows (messages, posts, versions, approvals, publications, media rows, model runs, console items, subscription). After the commit, the files under the business's storage prefix (`<businessId>/`) and the listed paths are deleted from storage; a storage error is logged, and the next run cannot retry it (the rows are gone), so it opens no item yet: deleting orphaned files by prefix is part of the media retention policy. Nothing about a deleted business remains in the database.
- **Monthly report.** The worker's `monthly-report` job runs at 06:00 UTC on the first of each month (08:00 or 09:00 in Israel), for the previous calendar month in the business's time zone (local midnight to local midnight). For every active business it takes the publications `published` with `published_at` in that month and asks `getMetrics` for each of their channel accounts over the month. Only metrics of those publications' provider posts count. It sends the owner the `monthly_report` template (variables `month`, `posts`, `reach`, `engagement`, where engagement is likes plus comments plus shares, and a metric the provider never supplied is `-`) when at least one post was published and the provider supplied at least one metric; otherwise nothing is sent. A provider error for one business is logged and does not stop the others.

## Console (Phase 1)

The UI is in English; conversation and caption text is shown in the business's language with `dir="auto"`, so Hebrew reads right to left. The page works on a phone (one column, the tabs stay on top) and on a desktop.

| Tab | What it shows |

| Conversations | Every business's WhatsApp conversation as a chat (searchable by name), with a side panel about the client: the profile, posts and drafts (every version with its hash and fact check, the approval state of each version, publications per network with their schedule, publish time, status and last error, and the rendered images), the conversation step and open question, agent turns with their steps, model runs with their cost, channel connections, and open console items. On a phone the list, the chat and the panel are separate views |

A model run opens on its own view (`?run=<id>`): task, prompt version, provider and model, attempt, tokens, cost, duration, validity, the error, and the input and output as JSON. An agent turn opens with its steps (each tool call and code's answer).

**Actions.** Every write records the signed-in team member. Writes that change configuration or a profile also add a row to `console_action` (database-schema.md) with the value before and after, in the same transaction. The console never approves a post version, never publishes, never changes an approval, and never changes the approver number; it shows the approval state only.

**Sign-in (WP-82).** The console runs as its own process (`main.js console`) and its own Cloud Run service; the public web service never serves it. Team members sign in with their Google accounts through Identity-Aware Proxy: on an external HTTPS load balancer in front of the console service in stage and prod (ingress internal and load balancer), and through Cloud Run's built-in IAP on the service in dev; never with a public invoker. The console verifies IAP's signed header `x-goog-iap-jwt-assertion` on every request (signature, audience, expiry) and refuses a request without a valid one (401). The verified email is the actor of every action: the global pause's `paused_by`, the price's `changed_by`, the cancellation, and a log line per action; a `by` in a request body is only a note. Locally and in tests a dev-only bypass (`CONSOLE_AUTH=dev-bypass`) answers only loopback addresses with a fixed actor, and refuses to start in stage or prod. Details: [security.md](security.md#console-exposure).

## Security

- **Request limits** (security.md D12): webhook bodies up to 256 KiB (413 before any signature check), console bodies up to 64 KiB; the console alone has a per-process limit per minute (300, provisional; 429). The webhooks are never rate-limited in the app, so unsigned floods cannot refuse genuine events; Cloud Armor is the planned flood guard.
- Row-level security on all business data, and each model call receives only that business's context.
- Provider tokens and secrets stay in a secret manager.
- Webhooks are verified before processing.
- Media URLs stay stable until publishing, and retention follows a defined policy.
- Payment card details are never stored.
- The console exposure and the ranked security debts are in [security.md](security.md).
- Logs are structured JSON from one shared logger, carry request, business, message and job ids, and never carry customer content, phone numbers or secrets; the logger redacts them in code ([observability.md](observability.md)).
- Metrics go to Cloud Monitoring and traces to Cloud Trace through OpenTelemetry, and every error log line is a Cloud Error Reporting event. Each metric is declared once with fixed label values, and span attributes are limited to ids and code words, so no customer content and no business id reach a label or an attribute ([observability.md](observability.md#metrics-wp-48)).

## Environments

- Local and test environments use simulators for WhatsApp, publishing, models, and payments. A local playground (WP-45) lets a human play the business owner against those simulators in a browser; it is never deployed.
- Dev and stage use test accounts and test keys only (dev on the simulators until then).
- Simulated mode (WP-51, [deployment.md](deployment.md#simulated-mode-dev-wp-51)): `POSTLY_PROVIDERS=simulators` runs web and worker on the messaging, publishing and payment simulators, with the model on Vertex AI in every deployed environment and on the model simulator in `local` and `test`, chosen by `POSTLY_ENV` with no switch. A deployed `POSTLY_ENV` refuses to start under `NODE_ENV=test` or `CI=true`. The agents always run; there is no flow switch ([deployment.md](deployment.md#real-gemini-and-the-agents-on-dev)). It is allowed only in `local`, `test` and `dev`; `stage` and `prod` refuse it at startup. In `dev` the simulators' state and stored media live in Postgres (`SIMULATOR_STORE=postgres`: the `simulator` schema, owned by its own login `app_simulator` with no grant on business tables), so web, worker and the sandbox share one outside world that survives restarts; each simulator call locks its state row for the call. A dev-only sandbox service, built from the playground and kept out of the product image, lets the human play the owner, see the mock feed, and pay, fail or cancel on a mock checkout page; it has no public invoker.
- Production access is limited and separate from agent environments.
- Dev, stage and production run on Google Cloud as described in [deployment.md](deployment.md): one image run as `web`, `worker` or `migrate`, Cloud Run, Cloud SQL with a private IP only, a private media bucket, and Secret Manager. Decided in WP-44: pg-boss connects as its own login `app_jobs`, which owns only the `pgboss` schema and has no grant on any business table; the migration job creates it and sets every login's password from Secret Manager. The weekly tick is an hourly pg-boss schedule on a singleton queue. Bursts are durable (the `message` claim and the `inbound-burst` job, Onboarding flow), so the web service may run several instances; the web process connects to pg-boss as `app_jobs` too. Nothing is deployed until the human applies it (gate H8).
