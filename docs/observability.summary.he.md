# תקציר: ניטור ולוגים

מסמך המקור: [observability.md](observability.md).

- **לוגר אחד** ב-`src/shared/logger.ts` לכל התהליכים (web, worker, console, migrate). אסור `console.*` במקום אחר ב-`src/`; בדיקה נכשלת אם יש.
- **פורמט:** שורת JSON אחת ב-stdout בפורמט ש-Google Cloud Logging קורא: `severity`, `message` קבוע באנגלית, `time`, שדה ה-trace, ו-labels עם המזהים.
- **מזהי קישור:** `AsyncLocalStorage` נושא את `requestId`, `businessId`, `messageId`, `jobId`, `jobName` ו-`process`. השרת פותח הקשר לכל בקשה, כל job רץ בהקשר משלו, וטיפול בהודעה נכנסת מוסיף את מזהי העסק וההודעה.
- **בלי תוכן לקוח, מספרי טלפון או סודות:** שדות בשמות כמו `text`, `phone`, `token`, `password` מוחלפים ב-`[redacted]`; בכל מחרוזת מוחלפים מספרי טלפון, סיסמאות ב-URL, טוקני Bearer ומחרוזות דמויות מפתח. מחרוזות נחתכות ב-500 תווים. בדיקה נכשלת אם תוכן או סוד מגיעים לשורת לוג.
- **שגיאות:** מעבירים ללוגר את אובייקט השגיאה עצמו (`{ error }`), לא `String(error)`. שגיאה, או אובייקט עם `message` (כמו ש-pg-boss שולח), נרשמת כשדות: ההודעה, `Name`, `Code`, `Cause` ו-`CauseCode`, אחרי ניקוי. `asError` הופך כל דבר שנזרק לשגיאה; אובייקט בלי `message` נרשם בלי שדותיו האחרים.
- **שגיאות מסד נתונים:** משגיאת שאילתה של Drizzle נשמרים רק ה-SQL ומספר הפרמטרים, בלי ערכי הפרמטרים (גוף הודעה, כיתוב), בהודעה, ב-stack ובכל cause; ערך שמצוטט אחרי נקודתיים בהודעת Postgres מוחלף ב-`[redacted]`.
- **שגיאות בנתיבים:** שרתי web וה-console רושמים כל שגיאה שהופכת ל-5xx בשורה `request failed` (נתיב, שיטה, סטטוס, מזהה בקשה), לפני התשובה; ה-sandbox רושם `sandbox request failed`, ותשובת ה-500 שלו מכילה רק את מזהה הבקשה.
- **שמירה:** 7 ימים ב-dev, 30 ב-stage וב-prod.
- **מעקב אחרי הודעה אחת:** `correlationId` אחד (מזהה שורת ההודעה הנכנסת; לרצף הודעות, מזהה ההודעה הראשונה) עובר מה-webhook, דרך משימת `inbound-burst`, אירועי ה-workflow, תור הסוכנת, קריאות המודל והכלים, ועד השליחה היוצאת. הוא נשמר גם בשורת הביקורת של אירועי ה-workflow. `correlationId` ו-`agentTurnId` הם labels כמו שאר המזהים.
- **שורות מחזור חיים:** הודעה נכנסת נשמרה, אירוע workflow הוחל או נדחה, תור סוכנת התחיל, קריאת כלי (תוצאה וקוד סירוב), הודעה יוצאת נשלחה או נכשלה, job התחיל, הסתיים או נכשל, וניסיון פרסום. רק מזהים, מצבים, מילות קוד ומשכי זמן, אף פעם לא תוכן. שורות התזמון (`inbound burst handled`, `agent step`, `agent turn ended`, `model call`) מתועדות בטבלה משלהן.
- **חומרה:** INFO לתוצאה צפויה (כולל סירוב מכוון), WARNING לבעיה שמתאוששת או תנוסה שוב, ERROR למה שדורש אדם.
- **`LOG_LEVEL`:** `debug`, `info`, `warn` או `error` (ברירת מחדל `info`). `debug` מותר רק ב-local, test ו-dev; stage ו-prod מסרבים לעלות איתו.
- **איך מנפים הודעה:** סעיף עם שאילתות מוכנות ל-Logs Explorer: לפי `correlationId`, `businessId` ו-`agentTurnId`, וכשלונות בשעה האחרונה, וגם ב-runbook.
- **מדדים (WP-48):** קטלוג אחד ב-`src/shared/telemetry.ts` (בדיקה משווה אותו לטבלה במסמך). בסביבות dev, stage ו-prod המדדים נשלחים ל-Cloud Monitoring בשם `workload.googleapis.com/postly.*`: הודעות נכנסות ויוצאות, טיוטות, אישורים, פרסומים לפי תוצאה ורשת, קריאות מודל עם עלות וזמן לכל משימה, משך jobs וכשלונות, ועומק תור. חיבורי מסד הנתונים נלקחים מהמדד של Cloud SQL.
- **בלי תוכן לקוח במדדים:** כל ערך label הוא מרשימה קבועה או קבוע מהקוד; ערך אחר הופך ל-`other`. אין label של מזהה עסק; תצוגה לפי עסק נבנית מהלוגים.
- **Tracing (WP-48):** Cloud Trace דרך OpenTelemetry, דגימה של 10%. spans לבקשה, ל-job, לקריאת מודל ולפרסום. רק מזהים ומילות קוד קצרות נכנסים כ-attributes; כל השאר נזרק. שורות לוג בתוך span נושאות את מזהי ה-trace וה-span.
- **Error Reporting (WP-48):** כל שורת לוג ברמת `ERROR` היא גם אירוע שגיאה (`@type` ו-`serviceContext`). שורת `ERROR` או `WARNING` עם שגיאה נושאת `stack_trace` אחרי ניקוי, כולל עד שתי סיבות (`Caused by`).
- **עומק התור:** ה-callback של המדד מוסר לפני ש-pg-boss נעצר, כך ש-worker שנכבה לא קורא תור סגור.

## לוחות מחוונים והתראות (WP-49)

- המודול `infra/modules/monitoring` מגדיר לכל סביבה (dev, stage, prod) את אותם לוחות ואותן התראות. CI מריץ `terraform validate` בלבד; אף סוכן לא מריץ `apply`.
- **מקורות:** מדדי המוצר של WP-48 (`workload.googleapis.com/postly.*`, בלי מזהה עסק), מדדים מבוססי לוגים משורות WP-47 (לפי `message` ו-`labels.businessId`), ומדדי Cloud Run ו-Cloud SQL המובנים.
- **מדדים מבוססי לוגים:** שורות שגיאה, אירועים לפי עסק (business_id, event, severity), שגיאות webhook לפי נתיב, וניתוק ערוץ (השורה `channel disconnected`, שבדיקת התקינות היומית של מודול הפרסום כותבת כשערוץ מתנתק).
- **לוחות:** סקירת שירות (בקשות, השהיה, 5xx, מופעים, CPU, זיכרון, חיבורים ודיסק של Cloud SQL); זרימת מוצר (הודעות נכנסות ויוצאות, טיוטות, אישורים, פרסומים לפי תוצאה, עלות והשהיה של המודל לפי משימה, תורים); ולוח לכל עסק עם מסנן `business_id`.
- **התראות חדשות:** שיעור כישלונות פרסום, שגיאות webhook, תור תקוע, worker לא רץ, ניתוק ערוץ, קפיצה בעלות המודל, קפיצה בכישלונות אימות של המודל, חיבורי Cloud SQL קרובים ל-`max_connections`, ושריפת תקציב השגיאות. לכל התראה קישור לסעיף שלה ב-`runbook.md`.
- **תקציב הסוכנת הכולל:** מדד לוג `postly-<env>-agent-global-budget` סופר את השורה `agent global budget reached` (WARNING), והתראה יורה על כל שורה כזו ב-10 דקות.
- **תקציב שגיאות:** SLO של 99.5% בקשות web בלי 5xx על פני 28 יום; ההתראה יורה כשקצב השריפה מעל פי 10 במשך שעה.
- **שורות תזמון (7.11.2026):** כדי לראות לאן הולך הזמן של כל תשובה, ב-INFO ובלי תוכן או מספרי טלפון: `inbound burst handled` לכל רצף (מספר ההודעות, חלון השקט, הזמן מהקבלה עד הנעילה, זמן הטיפול והזמן הכולל), `agent step` לכל צעד של הסוכנת (שמות הכלים, זמן המודל וזמן הכלים), `agent turn ended` לכל תור (סיבת העצירה, מספר הצעדים והקריאות, משך ועלות), `agent turn ended silent` (WARNING) לתור שלא אמר כלום ועבר לאדם, ו-`model call` לכל ניסיון מול המודל (משימה, מודל, גרסת פרומפט, משך, ניסיון, תוצאה, טוקני קלט, פלט וחשיבה; ניסיון לא תקין הוא WARNING ונושא את נתיבי השגיאה של Zod בלבד, `invalidPaths`, בלי הערכים). מפתח שמסתיים ב-`Tokens` נשמר רק כשהערך שלו מספר.
