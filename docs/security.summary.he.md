# אבטחה: תקציר בעברית

תקציר של [security.md](security.md). המסמך המלא באנגלית מחייב.

## מה קיים
- בידוד בין עסקים: RLS מאולץ בכל טבלה של עסק, וכל תפקיד הוא משתמש מסד נתונים נפרד עם הרשאות מינימליות.
- אימות HMAC לכל webhook; תהליך פרוס לא עולה בלי סוד אמיתי.
- סודות ב-Secret Manager; Cloud SQL בכתובת פרטית בלבד; שירות ה-web ציבורי, והקונסולה נגישה רק דרך load balancer עם IAP.

## חשיפת הקונסולה וכניסת צוות (WP-82)
- הקונסולה רצה כתהליך נפרד (`main.js console`) וכשירות Cloud Run נפרד; שירות ה-web הציבורי לא רושם את נתיבי הקונסולה (מחזיר 404).
- הכניסה היא דרך Google IAP: ‏load balancer חיצוני ב-HTTPS, ואחריו backend service עם IAP, ‏serverless NEG ושירות הקונסולה. ה-ingress של הקונסולה הוא "פנימי ו-load balancer", בלי `allUsers`; רק סוכן השירות של IAP מקבל `run.invoker`.
- מי נכנס: המשתנה `console_members` ב-Terraform (למשל `user:x@gmail.com` או `group:...`). ברירת המחדל ריקה.
- גם האפליקציה בודקת כל בקשה: את ה-JWT בכותרת `x-goog-iap-jwt-assertion` (חתימה מול המפתחות של Google, ה-audience מההגדרות, תוקף, ואימייל). בלי JWT תקין התשובה 401; בלי audience מוגדר כל בקשה נדחית.
- האימייל המאומת הוא מבצע הפעולה (D4): בהשהיה הכללית, בשינוי מחיר, בשורות ה-audit של אירועי workflow מהקונסולה (`team:<email>`), בפרטי העברה לאדם, ובשורת לוג לכל POST (כולל ביטול). השדה `by` בגוף הבקשה נשמר רק כהערה.
- מקומית ובבדיקות: `CONSOLE_AUTH=dev-bypass` (ברירת המחדל ב-local ו-test), רק loopback, והמבצע הוא `CONSOLE_DEV_ACTOR`. תהליך עם dev-bypass ב-stage או prod לא עולה.
- ההגנות מ-WP-80 (Host, ‏Origin, ‏JSON) נשארות.
- דומיין: המשתנה `console_domain` עם תעודה מנוהלת של Google. אפשר להתחיל בלי דומיין: Terraform משתמש בשם `sslip.io` שנגזר מכתובת ה-IP, רק ל-dev.
- OAuth: מסך הסכמה מסוג External ו-OAuth client נוצרים פעם אחת ידנית בכל פרויקט (ה-API של Google לזה הוצא משימוש). ה-client id נכנס ל-`console_iap_client_id` והסוד ל-Secret Manager. עד שה-client id מוגדר, Terraform לא יוצר load balancer והקונסולה לא נגישה.
- עלות: כ-18 דולר בחודש לכל סביבה עבור ה-load balancer.

## חובות טכניים (לפי סדר חשיבות)
1. D1: לא הייתה כניסה לקונסולה ולא זהות למבצע הפעולה. טופל בקוד ב-WP-82 (IAP); נכנס לתוקף כשהאדם מפעיל את ה-Terraform ושלב ה-OAuth.
2. D2: נתיב `cancel` מוחק עסק בלי הרשאה אמיתית.
3. D3: CSRF ו-DNS rebinding על הקונסולה המקומית.
4. D4: השדה `by` נלקח מגוף הבקשה. טופל ב-WP-82: המבצע הוא האימייל המאומת.
5. D5 (נסגר ב-T11): הרשאות ברמת עמודה למשתמש `console`, שלא יוכל להעביר שורה בין עסקים דרך `business_id`.
6. D6 (נסגר ב-T11): אחרי `CREATE ROLE ... IF NOT EXISTS` מגיע `ALTER ROLE` שקובע את מאפייני התפקיד.
7. D7: מספר החיבורים בכל ה-pools מול `max_connections` של Cloud SQL.
8. D8: `trustProxy` כבוי; אסור להסתמך על כתובת IP.
9. D9: הקונסולה רצה עם חשבון השירות של web וטוענת את כל הסיסמאות.
10. D10: `set_config` הוא סיכון מקובל, נתפס רק בבדיקת קוד המקור.
11. D11: הודעות נכנסות בזיכרון התהליך (T2).
12. D12: אין הגבלת קצב ונפח גוף בקשה.
13. D13: מדיה בזיכרון עד WP-41.
14. D14: לוגים עלולים להכיל תוכן לקוח (T14).
15. D15: TLS למסד הנתונים מוצפן אבל לא בודק את תעודת השרת (`sslmode=require` ב-postgres.js וב-pg-boss), כי התעודה של Cloud SQL חתומה ב-CA של המופע עצמו. המסד מקבל רק TLS ונגיש רק בכתובת פרטית בתוך ה-VPC. ההקשחה האפשרית: `verify-ca` עם ה-CA של המופע (פריט 52 בתור).

כל חוב הוא חבילת עבודה בתוכנית המימוש: D3 ‏WP-80, ‏D8 ‏WP-81, ‏D1 ו-D4 ‏WP-82, ‏D2 ‏WP-83, ‏D9 ‏WP-84, ‏D12 ‏WP-85, ‏D10 ‏WP-86, ‏D7 ‏WP-87; מכוסים: D5 ו-D6 ב-T11, ‏D11 ב-T2, ‏D13 ב-WP-41, ‏D14 ב-WP-47.

D2 טופל חלקית ב-WP-83: ביטול עסק מהקונסולה דורש הקלדת שם העסק; תיעוד מי ביטל ממתין לכניסת צוות (WP-82).
D3 טופל ב-WP-80: הקונסולה דוחה Host לא מוכר, Origin זר ובקשת POST שאינה JSON. אסימון CSRF יתווסף עם כניסת צוות.

D12 טופל ב-WP-85: מגבלת נפח לגוף בקשה (256KB ל-webhooks לפני בדיקת החתימה, ‏64KB לקונסולה) ומגבלת קצב לדקה לקונסולה בלבד. ל-webhooks אין מגבלת קצב באפליקציה, כדי שהצפה של בקשות לא חתומות לא תחסום הודעות אמיתיות; הגנה מהצפה תגיע עם Cloud Armor.
D8 טופל ב-WP-81: בסביבה הפרוסה web והקונסולה סומכים על קפיצת proxy אחת בלבד של Cloud Run; מקומית על אף אחת. בדיקת ה-loopback של הקונסולה קוראת את כתובת ה-socket ולעולם לא את X-Forwarded-For.

D9 טופל לקונסולה ב-WP-84: כל תהליך טוען רק את סיסמאות ההתחברות שלו, ולקונסולה חשבון שירות משלה שקורא רק אותן. web ו-worker עדיין טוענים הכול.
D10 נבדק מחדש ב-WP-86: מומלץ להשאיר את בדיקת קוד המקור ולהוסיף לה חסימת SQL דינמי (`sql.raw`, `.unsafe`, `.execute` עם מחרוזת), שמצמצמת את הפער ולא סוגרת אותו; ממתין לאישור האדם (H4).

D7 טופל ב-WP-87: גודל מאגר החיבורים מגיע מ-Terraform, תקציב החיבורים כולל גם את הקונסולה, וכל תהליך רושם בלוג כמה חיבורים לכל היותר הוא פותח.
