# Security

What protects Postly today, what is still missing, and the ranked list of security and operations debts that must be fixed before the stated milestone. Hebrew summary: [security.summary.he.md](security.summary.he.md).

This document refines the Security section of [technical-design.md](technical-design.md#security) and the IAM section of [deployment.md](deployment.md#iam-least-privilege). Nothing here has been applied in the cloud (gate H8).

## What is in place

- **Tenant isolation.** Every business-owned table has forced row-level security; code reaches Postgres only through `withBusiness(role, businessId, fn)` and `withSystem(purpose, fn)`, each role a separate login with only its tables and verbs ([database-schema.md](database-schema.md#least-privilege)). Raw SQL that changes roles or session settings is banned outside `src/db/` by `src/db/raw-sql-guard.test.ts`.
- **Webhooks** (messaging, payment) are verified by HMAC with a constant-time compare before processing. A deployed process refuses to start without a webhook secret or with the public simulator secret (`src/config.ts`).
- **Secrets** live in Secret Manager, one per database login, readable only by the service accounts that need them; `log_statement` stays `none` so login passwords never reach the logs ([deployment.md](deployment.md#architecture)).
- **Network.** Cloud SQL has a private IP only; the worker is a Cloud Run service with internal-only ingress; the web service is public, for the provider webhooks; the console is reachable only through a load balancer with IAP sign-in ([Console exposure](#console-exposure)).
- **Approval invariant and factual safeguards** are code-only paths, covered by the human-owned H5 tests.

## Console exposure

The console is its own process and Cloud Run service (T3), because Cloud Run ingress is set per service and the web service must stay public for the webhooks. Team members sign in through Google Identity-Aware Proxy (IAP) on an external HTTPS load balancer (WP-82; the human chose IAP over accounts in the app). Review queue item 16 accepted no sign-in only while the console was unreachable from the internet; this replaces that.

- **Process.** `node dist/src/main.js console` serves only the console routes and `/healthz` (`src/console-server.ts`). The `web` process never registers the console routes, so the public URL answers 404 for `/console` (`src/console-server.test.ts`).
- **Route.** `https://<console domain>` → a global external Application Load Balancer (a forwarding rule on port 443, a target HTTPS proxy with a Google-managed certificate and an SSL policy of TLS 1.2 or later) → a backend service with **IAP enabled** → a serverless network endpoint group → the `<prefix>-console` Cloud Run service. Terraform: `infra/modules/console_ingress`. There is no port 80 rule, so nothing answers plain HTTP.
- **Ingress.** The console service's ingress is `INGRESS_TRAFFIC_INTERNAL_LOAD_BALANCER`: requests from the internet reach it only through the load balancer, and its run.app URL refuses them. It still has no `allUsers` invoker; only IAP's service agent (`service-<project number>@gcp-sa-iap.iam.gserviceaccount.com`) has `roles/run.invoker` on it. It runs as its own `postly-<env>-console` service account, which reads only the passwords of the console process's logins and the webhook secret (D9, WP-84).
- **Who gets in.** The IAP access list is the Terraform variable `console_members` (for example `user:someone@gmail.com` or `group:team@example.com`), granted `roles/iap.httpsResourceAccessor` on the backend service only. It defaults to empty, so nobody passes IAP until the human names the team.
- **In the app (defense in depth).** Every console request must carry IAP's signed header `x-goog-iap-jwt-assertion`, and the console checks it even though only the load balancer can reach the service (`src/modules/console/iap.ts`): an ES256 signature from one of Google's IAP keys (`https://www.gstatic.com/iap/verify/public_key-jwk`, cached for an hour and fetched again for an unknown key id at most once a minute), issuer `https://cloud.google.com/iap`, audience equal to `CONSOLE_IAP_AUDIENCE` (`/projects/<project number>/global/backendServices/<backend service id>`, set by Terraform), not expired and not issued in the future (30 seconds of clock skew), and an `email`. A missing or invalid assertion gets 401. A console without a configured audience refuses every console request with 403 but still answers `/healthz`, so a half-configured service fails closed. The unsigned `x-goog-authenticated-user-email` header is never trusted.
- **The actor (D4).** The verified email is the actor of every console action: `system_control.paused_by` for the global pause, `plan_price.changed_by` for the price, `actor` = `team:<email>` on the workflow audit rows (WP-46) of the console's own events (pausing or resuming a business, retrying a publication), `by` in the details of a handoff the console starts, and one `console action` log line per `POST` (actor, method, path, status), which also covers the cancellation and resolving an item. Inside a route handler it is `consoleActor(request)`. A `by` field in a request body is no longer the actor; when it is given and differs from the actor, it is kept only as a note appended to the reason.
- **Locally and in tests.** `CONSOLE_AUTH=dev-bypass` (the default when `POSTLY_ENV` is `local` or `test`) skips the JWT, keeps the loopback-only check, and uses `CONSOLE_DEV_ACTOR` (default `local-dev`) as the actor. `dev`, `stage` and `prod` default to `iap`, and a process with `dev-bypass` and `POSTLY_ENV` `stage` or `prod` refuses to start (`src/config.ts`).
- **CSRF and DNS rebinding (D3, WP-80) stay.** IAP's session is a browser cookie, so the console still refuses a `Host` other than the console domain (`CONSOLE_HOST`, set by Terraform), a foreign or `null` `Origin`, and a non-JSON `POST`.
- **Domain and certificate.** The domain is the variable `console_domain`, served with a Google-managed certificate; the human points an `A` record at the load balancer's address (output `console_ip`), and the certificate becomes active within about an hour after the record resolves. **Starting without a domain:** leave `console_domain` unset and Terraform uses `<ip with dashes>.sslip.io`, a public wildcard DNS name that resolves to the address it contains, so the managed certificate works without owning a domain. Use it for dev only: whoever runs sslip.io could point the name elsewhere, get a certificate for it, and capture the IAP session cookie. Stage and prod need a real domain. (A self-signed certificate also works without a domain, but browsers warn on every visit.)
- **OAuth brand and client.** IAP for Google accounts outside a Google Workspace organization (for example gmail.com) needs an OAuth consent screen with the **External** user type and an OAuth client of your own. Google's IAP OAuth Admin API, which Terraform's `google_iap_brand` and `google_iap_client` use, is deprecated and only ever made Internal brands, so this is a one-time manual step per project ([deployment.md](deployment.md#console-sign-in-one-time-steps)). The client id goes into the variable `console_iap_client_id` and the client secret into the Secret Manager secret `postly-<env>-console-iap-client-secret`. Terraform reads that secret into the backend service's IAP settings, so it is also stored in the Terraform state (the private state bucket). **Until `console_iap_client_id` is set, Terraform creates no load balancer**, and the console is unreachable, which is the safe default and costs nothing.
- **Cost.** The load balancer's forwarding rule costs about 0.025 USD an hour, roughly **18 USD a month per environment**, plus about 0.008 USD per GB processed (negligible for the console). The managed certificate and IAP cost nothing.

The bastion VM of T3 is no longer needed and was never built.

## Technical debts (ranked)

Ranked by what can go wrong and how soon. "Before" names the milestone each one blocks. Each becomes a work package ([implementation-plan.md](implementation-plan.md#phase-5b-security-debts): D3 is WP-80, D8 WP-81, D1 and D4 WP-82, D2 WP-83, D9 WP-84, D12 WP-85, D10 WP-86, D7 WP-87; D5 and D6 are T11, D11 T2, D13 WP-41, D14 WP-47); the ones marked H4 or H8 need the human's review.

| # | Debt | Why it matters | Fix | Before |
| --- | --- | --- | --- | --- |
| D1 | **The console had no sign-in.** The loopback check and the internal ingress were network gates, not authentication; there was no user identity, so console actions had no actor. | Anyone with network access (locally) or `run.invoker` (deployed) can read every business's messages and drafts and cancel a business, which deletes all its data after the retention period. | Team sign-in (IAP on the console service, or accounts in the app), with the actor recorded on every action (ties into T13's audit trail). **Done in WP-82 as code** (IAP on an external load balancer, the JWT checked in the app, [Console exposure](#console-exposure)); it takes effect when the human applies the Terraform and does the OAuth step (H8). | Any console access beyond the founders; any public exposure |
| D2 | **`cancel` deletes a business with no real authorization.** `POST /console/api/businesses/:id/cancel` starts the cancellation and, 30 days later, the data deletion. | Irreversible customer data loss from one unauthenticated request. | Requires D1; add a confirmation step (typed business name or second request) and the actor in the record. **Confirmation done in WP-83:** the route needs `confirmName` equal to the business name (trimmed), else 400; the actor waits for WP-82. | Any public exposure of the console |
| D3 | **CSRF and DNS rebinding on the console.** The JSON API takes `POST`s with no CSRF token, no `Origin` or `Host` check. | Locally, a web page the team member visits can make the browser call `http://127.0.0.1:<port>/console/api/...`; with DNS rebinding a hostile page can also read the answers. | D4 | **`by` comes from the request body.** The global pause records `by` from `PauseBody`, which the caller types. | The pause record can name anyone; it is not an audit trail. | Take the actor from the signed-in identity (D1); keep the body field only as a note. **Done in WP-82:** the actor is the IAP email (locally `CONSOLE_DEV_ACTOR`); a body `by` is only appended to the reason as a note. | D1 |

H4. | Closed |
| D7 | **Pool count against Cloud SQL `max_connections`.** Each process opens one pool per login: 15 logins (10 business roles, 4 system purposes, `app_jobs`), up to 3 connections each by default plus pg-boss's own pool. | D8 | **`trustProxy` is off.** Fastify sees Cloud Run's front end as the client, so `request.ip` is never the real caller. | Any future IP-based rule (rate limits, allowlists, logs) would be wrong; turning `trustProxy: true` on blindly lets a caller spoof `X-Forwarded-For`. | Set `trustProxy` to Cloud Run's hop count only, and never use the IP as authentication. **Done in WP-81:** deployed web and console trust exactly one hop (`trustProxyHops`), local runs none. The console's loopback gate reads the socket's remote address, never `X-Forwarded-For`, whatever `trustProxy` is set to. | Any IP-based rule |
| D9 | **The console runs as the web service account and loads every login's password.** `loadConfig` requires all 15 passwords for every process. | The console (and the worker) can read secrets they never use; a bug in one process reaches every role. | Per-process config: each command reads only the passwords of the roles it uses; give the console its own service account that reads only the passwords of the logins its actions use. | D10 | **`set_config` is an accepted risk.** The business context is a session setting; raw `set_config('app.business_id', ...)` to another business is caught only by the source guard, not by the database (`src/db/tenant-isolation.db.test.ts`, "known gap"). | A raw query that slips past the guard (dynamic SQL, a new driver) can read another business's rows within the role's grants. | Keep the guard; consider signed context (a role per business is too many) or `SECURITY DEFINER` setters checked against the role. | D11 | **Inbound bursts live in process memory** (review queue items 14 and 24). | Two web instances can hand a burst over twice; a restart inside the quiet window relies on the sweep. | The durable claim (T2). | A second web instance |
| D12 | **No rate limit or body-size limit beyond Fastify's defaults** on the webhooks and the console. | A flood of signed-looking requests costs CPU on HMAC checks; large bodies use memory. | A per-route `bodyLimit` and a simple rate limit on the public routes (or Cloud Armor in front of web). | Public launch |

| D14 | **Logs may carry customer content.** Error lines include `String(error)`, which can quote message text or provider answers. | Customer data in logs outlives the retention period. | Structured logging that strips content (T14). | T14 |
