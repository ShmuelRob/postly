# Security

What protects Postly today, what is still missing, and the ranked list of security and operations debts that must be fixed before the stated milestone. Hebrew summary: [security.summary.he.md](security.summary.he.md).

This document refines the Security section of [technical-design.md](technical-design.md#security) and the IAM section of [deployment.md](deployment.md#iam-least-privilege). Nothing here has been applied in the cloud (gate H8).

## What is in place

- **Tenant isolation.** Every business-owned table has forced row-level security; code reaches Postgres only through `withBusiness(role, businessId, fn)` and `withSystem(purpose, fn)`, each role a separate login with only its tables and verbs ([database-schema.md](database-schema.md#least-privilege)). Raw SQL that changes roles or session settings is banned outside `src/db/` by `src/db/raw-sql-guard.test.ts`.
- **Webhooks** (messaging, payment) are verified by HMAC with a constant-time compare before processing. A deployed process refuses to start without a webhook secret or with the public simulator secret (`src/config.ts`).
- **Secrets** live in Secret Manager, one per database login, readable only by the service accounts that need them; `log_statement` stays `none` so login passwords never reach the logs ([deployment.md](deployment.md#architecture)).
- **Network.** Cloud SQL has a private IP only; the worker is a Cloud Run service with internal-only ingress; the web service is public, for the provider webhooks; the console is reachable only through IAP sign-in, on a load balancer in stage and prod and through Cloud Run's built-in IAP on dev ([Console exposure](#console-exposure)); the dev-only sandbox only by its listed accounts, through Cloud Run's built-in IAP or `gcloud run services proxy`, unless dev's `sandbox_public` switch opens it to anyone with the link ([Sandbox exposure](#sandbox-exposure)).
- **Approval invariant and factual safeguards** are code-only paths, covered by the human-owned H5 tests.

## Console exposure

The console is its own process and Cloud Run service (T3), because Cloud Run ingress is set per service and the web service must stay public for the webhooks. Team members sign in through Google Identity-Aware Proxy (IAP) (WP-82; the human chose IAP over accounts in the app): on an external HTTPS load balancer in stage and prod, and through Cloud Run's built-in IAP on the service itself in dev. Review queue item 16 accepted no sign-in only while the console was unreachable from the internet; this replaces that.

- **Process.** `node dist/src/main.js console` serves only the console routes and `/healthz` (`src/console-server.ts`). The `web` process never registers the console routes, so the public URL answers 404 for `/console` (`src/console-server.test.ts`).
- **Route (stage, prod).** `https://<console domain>` → a global external Application Load Balancer (a forwarding rule on port 443, a target HTTPS proxy with a Google-managed certificate and an SSL policy of TLS 1.2 or later) → a backend service with **IAP enabled** → a serverless network endpoint group → the `<prefix>-console` Cloud Run service. Terraform: `infra/modules/console_ingress`. There is no port 80 rule, so nothing answers plain HTTP.
- **Route (dev).** `https://postly-dev-console-<project number>.me-west1.run.app/console` → Cloud Run's built-in IAP (`iap_enabled` on the service, variable `cloud_run_iap`) → the console. No load balancer, no domain and no certificate to manage (Cloud Run serves run.app over HTTPS), and no cost. Terraform refuses `cloud_run_iap` outside dev and together with `console_iap_client_id`, because IAP cannot guard both the load balancer and the service. Details: [deployment.md](deployment.md#browser-sign-in-on-dev).
- **Ingress.** In stage and prod the console service's ingress is `INGRESS_TRAFFIC_INTERNAL_LOAD_BALANCER`: requests from the internet reach it only through the load balancer, and its run.app URL refuses them. In dev it is "all", so the run.app URL answers, and Cloud Run's IAP checks every request before it reaches the service. It still has no `allUsers` invoker; only IAP's service agent (`service-<project number>@gcp-sa-iap.iam.gserviceaccount.com`) has `roles/run.invoker` on it. It runs as its own `postly-<env>-console` service account, which reads only the passwords of the console process's logins and the webhook secret (D9, WP-84).
- **Who gets in.** The IAP access list is the Terraform variable `console_members` (for example `user:someone@gmail.com` or `group:team@example.com`), granted `roles/iap.httpsResourceAccessor` on the backend service (stage, prod) or on the console's Cloud Run service (dev) only. It defaults to empty in stage and prod, so nobody passes IAP until the human names the team; dev defaults it to `sandbox_invokers` (the human). Terraform refuses `allUsers` and `allAuthenticatedUsers` in it.
- **In the app (defense in depth).** Every console request must carry IAP's signed header `x-goog-iap-jwt-assertion`, and the console checks it even though only the load balancer can reach the service (`src/modules/console/iap.ts`): an ES256 signature from one of Google's IAP keys (`https://www.gstatic.com/iap/verify/public_key-jwk`, cached for an hour and fetched again for an unknown key id at most once a minute), issuer `https://cloud.google.com/iap`, audience equal to `CONSOLE_IAP_AUDIENCE` (set by Terraform: `/projects/<project number>/global/backendServices/<backend service id>` behind the load balancer, `/projects/<project number>/locations/<region>/services/<prefix>-console` with Cloud Run's built-in IAP; the console refuses any other form at startup, and a token IAP signed for another service, such as the sandbox, fails the exact match), not expired and not issued in the future (30 seconds of clock skew), and an `email`. A missing or invalid assertion gets 401. A console without a configured audience refuses every console request with 403 but still answers `/healthz`, so a half-configured service fails closed. The unsigned `x-goog-authenticated-user-email` header is never trusted.
- **The actor (D4).** The verified email is the actor of every console action: `system_control.paused_by` for the global pause, `plan_price.changed_by` for the price, `actor` = `team:<email>` on the workflow audit rows (WP-46) of the console's own events (pausing or resuming a business, retrying a publication), `by` in the details of a handoff the console starts, and one `console action` log line per `POST` (actor, method, path, status), which also covers the cancellation and resolving an item. Inside a route handler it is `consoleActor(request)`. A `by` field in a request body is no longer the actor; when it is given and differs from the actor, it is kept only as a note appended to the reason.
- **Locally and in tests.** `CONSOLE_AUTH=dev-bypass` (the default when `POSTLY_ENV` is `local` or `test`) skips the JWT, keeps the loopback-only check, and uses `CONSOLE_DEV_ACTOR` (default `local-dev`) as the actor. `dev`, `stage` and `prod` default to `iap`, and a process with `dev-bypass` and `POSTLY_ENV` `stage` or `prod` refuses to start (`src/config.ts`).
- **Media in the console.** Rendered images and customer media (photos, logos) open only through `GET /console/media/:assetId`, a console route behind the same IAP check as every other request: the console process reads the bytes of the `media_asset`'s storage path. The stored type comes from the messaging provider or the owner's upload and is never trusted (stored XSS: an SVG or HTML file served inline would run script on the console's origin). Only the raster image types the page shows, `image/png`, `image/jpeg`, `image/webp` and `image/gif`, are served inline with that type; anything else is served as `application/octet-stream` with `Content-Disposition: attachment`. Every media response carries `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox`. The console never links to a public media URL and never makes an object public. When WP-41 moves media to Cloud Storage, this route reads the private object (D13).
- **What the console may change.** Configuration (the agent limits, the agent daily cost cap, the model task settings, the price), a business's profile (never its approver number), pauses, handoffs and the review queue. Every such write records the actor, and the configuration and profile writes add a `console_action` row with the value before and after. It never approves a post version, publishes, or changes an approval ([technical-design.md](technical-design.md#console-phase-1)).
- **CSRF and DNS rebinding (D3, WP-80) stay.** IAP's session is a browser cookie, so the console still refuses a `Host` other than the console domain or, on dev, its deterministic run.app host (`CONSOLE_HOST`, set by Terraform), a foreign or `null` `Origin`, and a non-JSON `POST`.
- **Domain and certificate (stage, prod).** The domain is the variable `console_domain`, served with a Google-managed certificate; the human points an `A` record at the load balancer's address (output `console_ip`), and the certificate becomes active within about an hour after the record resolves. **Starting without a domain:** leave `console_domain` unset and Terraform uses `<ip with dashes>.sslip.io`, a public wildcard DNS name that resolves to the address it contains, so the managed certificate works without owning a domain. Use it for dev only: whoever runs sslip.io could point the name elsewhere, get a certificate for it, and capture the IAP session cookie. Stage and prod need a real domain. (A self-signed certificate also works without a domain, but browsers warn on every visit.)
- **OAuth brand and client.** IAP for Google accounts outside a Google Workspace organization (for example gmail.com) needs an OAuth consent screen with the **External** user type and an OAuth client of your own. Google's IAP OAuth Admin API, which Terraform's `google_iap_brand` and `google_iap_client` use, is deprecated and only ever made Internal brands, so this is a one-time manual step per project ([deployment.md](deployment.md#console-sign-in-one-time-steps)). On dev, the Cloud console's "Auto generate credentials" makes the client and stores it in the project-level IAP settings that the console and the sandbox share, so no client id or secret reaches Terraform or its state ([deployment.md](deployment.md#browser-sign-in-on-dev)). The client id goes into the variable `console_iap_client_id` and the client secret into the Secret Manager secret `postly-<env>-console-iap-client-secret`. Terraform reads that secret into the backend service's IAP settings, so it is also stored in the Terraform state (the private state bucket). **Until `console_iap_client_id` is set, Terraform creates no load balancer**, and the console is unreachable, which is the safe default and costs nothing.
- **Cost.** Dev's built-in IAP costs nothing. The load balancer's forwarding rule costs about 0.025 USD an hour, roughly **18 USD a month per environment**, plus about 0.008 USD per GB processed (negligible for the console). The managed certificate and IAP cost nothing.

The bastion VM of T3 is no longer needed and was never built.

## Sandbox exposure

The dev sandbox (WP-51, [deployment.md](deployment.md#the-sandbox)) acts as the business owner on the simulators: it posts signed owner messages to the web service and approves drafts. It exists only in dev (Terraform refuses `sandbox_enabled` elsewhere) and touches no real customer, channel or payment.

- **Not public by default.** No `allUsers` or `allAuthenticatedUsers` binding; Terraform refuses both in `sandbox_invokers` and `sandbox_members`. Its ingress is "all", because both ways in reach its run.app URL from the internet; the IAM checks below gate every request.
- **Public switch (`sandbox_public`, dev only, off by default).** Since 2026-11-09 the human may open the sandbox to anyone with its link, with no Google sign-in, for a while. `sandbox_public = true` in dev's `terraform.tfvars` turns off `iap_enabled` on `postly-dev-sandbox` only and adds one `roles/run.invoker` grant to `allUsers` on it (the `cloud_run` module's `public` input); Terraform refuses the switch outside dev or without the sandbox. Everything else stays: the IAP grants to `sandbox_members`, IAP's service agent's invoker grant, the project's OAuth client and IAP settings, `cloud_run_iap`, `SANDBOX_URL` (the run.app URL), and the console, which stays behind IAP. **Risk while it is on:** anyone who has or guesses the URL can chat with the dev agent as the owner, start new sign-ups, and see the sandbox's dev test data (the owner chat, the simulated feed and checkout); every message makes paid Vertex AI calls on dev, bounded only by dev's monthly budget alert (`model_budget_usd`), which alerts and does not stop spending. Dev runs on the simulators, so no real customer, WhatsApp number, social account or payment is reachable. **To turn it off:** delete the line or set `sandbox_public = false`, then `terraform -chdir=infra/environments/dev plan -out dev.tfplan` (expect `iap_enabled` back to true on the sandbox and the `allUsers` grant destroyed) and `apply dev.tfplan`; sign-in works again at once, with nothing to redo by hand.
- **Browser (`cloud_run_iap`, dev's default).** Cloud Run's built-in IAP on the service (no load balancer, no extra cost). The accounts in `sandbox_members` (default: `sandbox_invokers`) get `roles/iap.httpsResourceAccessor` on the sandbox service only, and IAP's service agent gets `roles/run.invoker` on it. IAP uses the project's own OAuth client with an External consent screen (Google's managed client admits only users inside an organization, and a gmail.com account has none), made once in the Cloud console and kept in the project-level IAP settings; no client secret is in Terraform or its state.
- **Proxy.** Each account in `sandbox_invokers` has `roles/run.invoker` on the sandbox service only; `gcloud run services proxy` adds that account's identity token, and Cloud Run refuses anyone else with 403. With IAP on, IAP checks first, and gcloud's OAuth client is no longer an IAP programmatic client, so the proxy may not get through; that only narrows access.
- **Publish now (dev demos).** `POST /api/publish-now` moves the current sign-up's `scheduled` publications to now, through the `console` system role's existing manual-scheduling grant on `publication` (no new grant). It cannot publish an unapproved post: the publishing job still checks the approved version hash and the pauses. It exists only in the sandbox service and refuses outside `local`, `test` and `dev`. With `sandbox_public` on, anyone with the link can press it, which only moves the demo's simulated posts forward.
- **No identity check in the app.** Unlike the console, the sandbox does not verify IAP's signed header: it has no per-user behavior, and everyone who passes is a `sandbox_invokers` account playing the one owner number. A wrong IAM binding would expose only simulated dev data and the owner's dev chat.
- **CSRF.** With IAP the session is a browser cookie (with `sandbox_public` there is no session to abuse: anyone may post anyway), so the sandbox refuses an `/api/` `POST` whose `Origin` is present and is neither its own host nor a loopback address (the proxy's `http://localhost:8081` page) (403; `playground/sandbox/origin.ts`). Without it, a page the human visits could sign up a new business or send messages as the owner.

## Technical debts (ranked)

Ranked by what can go wrong and how soon. "Before" names the milestone each one blocks. Each becomes a work package ([implementation-plan.md](implementation-plan.md#phase-5b-security-debts): D3 is WP-80, D8 WP-81, D1 and D4 WP-82, D2 WP-83, D9 WP-84, D12 WP-85, D10 WP-86, D7 WP-87; D5 and D6 are T11, D11 T2, D13 WP-41, D14 WP-47); the ones marked H4 or H8 need the human's review.

| D1 | **The console had no sign-in.** The loopback check and the internal ingress were network gates, not authentication; there was no user identity, so console actions had no actor. | Anyone with network access (locally) or `run.invoker` (deployed) can read every business's messages and drafts and cancel a business, which deletes all its data after the retention period. | Team sign-in (IAP on the console service, or accounts in the app), with the actor recorded on every action (ties into T13's audit trail). **Done in WP-82 as code** (IAP on an external load balancer, the JWT checked in the app, [Console exposure](#console-exposure)); it takes effect when the human applies the Terraform and does the OAuth step (H8). | Any console access beyond the founders; any public exposure |
