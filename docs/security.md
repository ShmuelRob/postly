# Security

What protects Postly today, what is still missing, and the ranked list of security and operations debts that must be fixed before the stated milestone. Hebrew summary: [security.summary.he.md](security.summary.he.md).

This document refines the Security section of [technical-design.md](technical-design.md#security) and the IAM section of [deployment.md](deployment.md#iam-least-privilege). Nothing here has been applied in the cloud (gate H8).

## What is in place

- **Tenant isolation.** Every business-owned table has forced row-level security; code reaches Postgres only through `withBusiness(role, businessId, fn)` and `withSystem(purpose, fn)`, each role a separate login with only its tables and verbs ([database-schema.md](database-schema.md#least-privilege)). Raw SQL that changes roles or session settings is banned outside `src/db/` by `src/db/raw-sql-guard.test.ts`.
- **Webhooks** (messaging, payment) are verified by HMAC with a constant-time compare before processing. A deployed process refuses to start without a webhook secret or with the public simulator secret (`src/config.ts`).
- **Secrets** live in Secret Manager, one per database login, readable only by the service accounts that need them; `log_statement` stays `none` so login passwords never reach the logs ([deployment.md](deployment.md#architecture)).
- **Network.** Cloud SQL has a private IP only; the worker and the console are Cloud Run services with internal-only ingress; only the web service is public, for the provider webhooks.
- **Approval invariant and factual safeguards** are code-only paths, covered by the human-owned H5 tests.

## Console exposure

The console has no team sign-in yet (review queue item 16; the human accepted that for now on the condition that it is never reachable from the internet). Cloud Run ingress is set per service, and the web service must stay public for the webhooks, so the console cannot share it.

Decision (T3): the console is its own process and Cloud Run service.

- **Process.** `node dist/src/main.js console` serves only the console routes and `/healthz` (`src/console-server.ts`). The `web` process never registers the console routes, so the public URL answers 404 for `/console` (`src/console-server.test.ts`).
- **Service.** `<prefix>-console` has ingress `INGRESS_TRAFFIC_INTERNAL_ONLY` and no `allUsers` invoker, so a request needs both a path from inside the VPC and the `roles/run.invoker` IAM role. It runs as its own `postly-<env>-console` service account, which reads only the passwords of the console process's logins (D9, WP-84).
- **In the app.** Locally (`POSTLY_ENV` `local` or `test`) the routes keep answering only loopback addresses. Deployed, the gate is the ingress and IAM (`access: 'private-ingress'`), because behind Cloud Run's front end no request comes from loopback.
- **Reaching it.** Not from a laptop through the run.app URL or `gcloud run services proxy`: both go through Cloud Run's public front end, which internal-only ingress refuses. The working path for now is a small bastion VM inside the VPC, reached with `gcloud compute ssh --tunnel-through-iap`, that calls the service's internal URL with an identity token (`curl -H "Authorization: Bearer $(gcloud auth print-identity-token)" ...`, or an SSH port forward for the browser). The bastion is not in Terraform yet; adding it, or an internal load balancer, or IAP on an external load balancer with sign-in (D1), is a follow-up. Until then the deployed console is unreachable, which is the safe default.

This is a network gate, not a sign-in: anyone holding `run.invoker` on the project can use every console action, including cancelling a business, and the console does not know who acted. Real sign-in (for example IAP with Google accounts, or team accounts) replaces it before any wider access (D1).

## Technical debts (ranked)

Ranked by what can go wrong and how soon. "Before" names the milestone each one blocks. Each becomes a work package ([implementation-plan.md](implementation-plan.md#phase-5b-security-debts): D3 is WP-80, D8 WP-81, D1 and D4 WP-82, D2 WP-83, D9 WP-84, D12 WP-85, D10 WP-86, D7 WP-87; D5 and D6 are T11, D11 T2, D13 WP-41, D14 WP-47); the ones marked H4 or H8 need the human's review.

| # | Debt | Why it matters | Fix | Before |
| --- | --- | --- | --- | --- |
| D1 | **The console has no sign-in.** The loopback check and the internal ingress are network gates, not authentication; there is no user identity, so console actions have no actor. | Anyone with network access (locally) or `run.invoker` (deployed) can read every business's messages and drafts and cancel a business, which deletes all its data after the retention period. | Team sign-in (IAP on the console service, or accounts in the app), with the actor recorded on every action (ties into T13's audit trail). | Any console access beyond the founders; any public exposure |
| D2 | **`cancel` deletes a business with no real authorization.** `POST /console/api/businesses/:id/cancel` starts the cancellation and, 30 days later, the data deletion. | Irreversible customer data loss from one unauthenticated request. | Requires D1; add a confirmation step (typed business name or second request) and the actor in the record. | Any public exposure of the console |
| D3 | **CSRF and DNS rebinding on the console.** The JSON API takes `POST`s with no CSRF token, no `Origin` or `Host` check. | Locally, a web page the team member visits can make the browser call `http://127.0.0.1:<port>/console/api/...`; with DNS rebinding a hostile page can also read the answers. The loopback check does not stop either. | Check `Host` against an allowlist and `Origin` on every non-`GET`; require a JSON content type; add a CSRF token once there is a session. **Done in WP-80** except the token: the console refuses an unknown `Host` (loopback names locally, `allowedHosts` deployed), a foreign or `null` `Origin`, and a non-JSON `POST`. | Running the console on a laptop that browses the web |
| D4 | **`by` comes from the request body.** The global pause records `by` from `PauseBody`, which the caller types. | The pause record can name anyone; it is not an audit trail. | Take the actor from the signed-in identity (D1); keep the body field only as a note. | D1 |
| D5 | **Console column-level grants (T11). Closed.** The `console` login could update whole rows of the tables it writes, including `business_id`. | A bug or a crafted call could have moved a row to another business. | Done in migration 0013: on business-owned tables the `console` login may update every column except `id` and `business_id`; `src/db/least-privilege.db.test.ts` checks the grants and that the forbidden updates are refused. H4. | Closed |
| D6 | **`CREATE ROLE ... IF NOT EXISTS` did not set attributes (T11). Closed.** A role that already existed kept its attributes. | A pre-existing role with `INHERIT`, `CREATEROLE` or `BYPASSRLS` would have kept them silently. | Done in migration 0013, and in `src/db/provision.ts` for `app_jobs`: an `ALTER ROLE` after each creation sets `LOGIN NOINHERIT NOCREATEROLE NOCREATEDB`, with `BYPASSRLS` only for the system logins. H4. | Closed |
| D7 | **Pool count against Cloud SQL `max_connections`.** Each process opens one pool per login: 15 logins (10 business roles, 4 system purposes, `app_jobs`), up to 3 connections each by default plus pg-boss's own pool. Web, worker and console together can ask for well over 100 connections. | `db-f1-micro` allows about 25 connections and `db-g1-small` about 50; under load connections fail with `too many clients`, which looks like random errors. | Size pools per process (the console and worker need few roles), set `max` per login from config, and add a check (test or startup log) that the sum stays under the tier's limit with headroom; adjust with T4's tiers. **Done in WP-87** (with T4's Terraform check): `DB_POOL_MAX` comes from Terraform's `pool_max`, the budget counts the console service (capped at one instance), `src/process-logins-infra.test.ts` keeps code and Terraform in step, and each process logs its `maxConnections` at startup. | First deploy with real traffic |
| D8 | **`trustProxy` is off.** Fastify sees Cloud Run's front end as the client, so `request.ip` is never the real caller. | Any future IP-based rule (rate limits, allowlists, logs) would be wrong; turning `trustProxy: true` on blindly lets a caller spoof `X-Forwarded-For`. | Set `trustProxy` to Cloud Run's hop count only, and never use the IP as authentication. | Any IP-based rule |
| D9 | **The console runs as the web service account and loads every login's password.** `loadConfig` requires all 15 passwords for every process. | The console (and the worker) can read secrets they never use; a bug in one process reaches every role. | Per-process config: each command reads only the passwords of the roles it uses; give the console its own service account that reads only the passwords of the logins its actions use. H8. **Console done in WP-84:** `PROCESS_LOGINS` in `src/db/index.ts` lists each process's logins and `loadConfig(env, process)` reads only those; the console has its own `postly-<env>-console` account that reads only its six logins' passwords and the webhook secret. Web and worker still load every login until narrowed the same way. | Before D1 widens access |
| D10 | **`set_config` is an accepted risk.** The business context is a session setting; raw `set_config('app.business_id', ...)` to another business is caught only by the source guard, not by the database (`src/db/tenant-isolation.db.test.ts`, "known gap"). | A raw query that slips past the guard (dynamic SQL, a new driver) can read another business's rows within the role's grants. | Keep the guard; consider signed context (a role per business is too many) or `SECURITY DEFINER` setters checked against the role. Accepted risk, reviewed again with D5. | Re-review at the next H4 |
| D11 | **Inbound bursts live in process memory** (review queue items 14 and 24). | Two web instances can hand a burst over twice; a restart inside the quiet window relies on the sweep. | The durable claim (T2). | A second web instance |
| D12 | **No rate limit or body-size limit beyond Fastify's defaults** on the webhooks and the console. | A flood of signed-looking requests costs CPU on HMAC checks; large bodies use memory. | A per-route `bodyLimit` and a simple rate limit on the public routes (or Cloud Armor in front of web). | Public launch |
| D13 | **Media is in process memory until WP-41.** | Nothing persists; once Cloud Storage lands, media URLs need signed or private access as the retention policy says. | WP-41's Cloud Storage adapter with signed URLs. | WP-41 |
| D14 | **Logs may carry customer content.** Error lines include `String(error)`, which can quote message text or provider answers. | Customer data in logs outlives the retention period. | Structured logging that strips content (T14). | T14 |

Known decisions that are not debts: no card data is ever stored (the payment provider holds it); the deploy account can reach data indirectly, gated by GitHub environments ([deployment.md](deployment.md#iam-least-privilege)).
