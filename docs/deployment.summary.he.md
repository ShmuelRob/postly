# פריסה: עיקרי הדברים

תקציר של [deployment.md](deployment.md). שום דבר עוד לא נפרס: סוכנים כותבים ומאמתים את הקוד בלבד, ויצירת משאבים בענן, הוצאת כסף ופריסה ממתינים לאדם (נקודת אישור H8).

- **אימג' אחד:** Node 26 עם Chromium של Playwright ו-sharp, רץ כמשתמש שאינו root. הפקודה בוחרת תהליך: `web` (Fastify, ה-webhooks), `worker` (pg-boss), `console` (הקונסולה הפנימית, שירות נפרד עם ingress פנימי ו-load balancer, בלי גישה ציבורית; הצוות נכנס דרך load balancer עם IAP, ראו [security.summary.he.md](security.summary.he.md)) או `migrate` (משימת המיגרציה). קוד הבדיקות וה-playground לא נכנסים לאימג'.
- **ה-worker:** מריץ את `WeeklyUpdates.tick` כל שעה עגולה, בתור pg-boss במדיניות singleton, כך שגם עם כמה מופעים רץ רק tick אחד בכל רגע.
- **משימת המיגרציה:** מריצה את המיגרציות (שיוצרות משתמש מסד נתונים לכל תפקיד), קובעת את הסיסמאות מ-Secret Manager, ויוצרת משתמש נפרד ל-pg-boss. Terraform לא יוצר תפקידים במסד.
- **Terraform:** מודולים לרשת פרטית, Artifact Registry, חשבונות שירות בהרשאות מינימליות, Secret Manager (שמות בלבד, בלי ערכים), Cloud SQL עם כתובת פרטית בלבד, דלי מדיה פרטי עם מחזור חיים, Cloud Run ל-web ול-worker, וניטור: התראות, מדדים מבוססי לוגים, SLO לזמינות ה-web ושלושה לוחות מחוונים (observability.md). שלוש סביבות: dev (זולה, תמיד פעילה, על סימולטורים או חשבונות בדיקה, פריסה אוטומטית בלי מאשר מענף `dev`, מופע אחד, אותם גדלים כמו stage ו-prod, לוגים נשמרים 7 ימים, וזה חל על כל הפרויקט, לכן ל-dev פרויקט משלו), stage (בדיקה לפני prod על חשבונות בדיקה) ו-prod; Terraform גם מפעיל את ה-APIs, מייצר סיסמאות אקראיות לכל משתמשי המסד, לסוד ה-webhook ולמשתמש ה-postgres (וכותב מהם את כתובת המנהל), יוצר את סביבות GitHub עם המשתנים, ושורש `infra/bootstrap` יוצר דלי state פרטי עם גרסאות. הסודות שנוצרו נמצאים ב-state, וזה מקובל רק כי הדלי פרטי ועם גרסאות.
- **גדלים (פריטים 21, 23 בתור):** כל הסביבות בגודל בינוני-נמוך באזור `me-west1` (תל אביב), בלי רפליקות ובלי HA: Cloud SQL `db-custom-2-7680` (2 vCPU, 7.5GB, `max_connections` 400), web עם 1 vCPU ו-2GiB (מופע אחד), worker עם 2 vCPU ו-4GiB (עד מופע אחד, ב-prod עד שניים). הגדלים בתוך המגבלות של GCP (ב-Cloud Run מעל 4GiB צריך לפחות 2 vCPU; ב-Cloud SQL בין 0.9 ל-6.5GB לכל vCPU). Terraform בודק שסך החיבורים (55 לכל תהליך: 15 משתמשים כפול 3, ועוד 10 של pg-boss, ועוד job ההגירה ומרווח) לא עובר את `max_connections`.
- **מחזור חיים של המדיה:** גיל המעבר ל-Coldline ארוך מתקופת השמירה של 30 יום אחרי ביטול: מעבר ל-Coldline אחרי 180 יום. גרסאות ישנות (כולל קבצים שנמחקו) נמחקות אחרי 7 ימים, כך שמדיה שנמחקה ביום 30 נעלמת עד יום 37 בערך. רק קבצים זמניים ב-`tmp/` נמחקים אחרי יום.
- **מי ממזג ומי מאשר פריסה (מקובל כרגע):** כל הסוכנים מריצים `gh` כחשבון של האדם, שהוא המאשר היחיד ומנהל המאגר, כך ש-GitHub לבד לא מונע מסוכן לאשר פריסה. הכלל: רק סשן הסוקר ממזג PRs, כולל PRs של קידום (`dev` ל-`stage`, `stage` ל-`main`); שאר הסוכנים רק פותחים PRs. אף סוכן לא מאשר פריסה ל-stage או ל-prod, רק האדם. בהמשך אפשר לחזק עם זהות GitHub נפרדת לסוכנים בלי הרשאות ניהול או אישור.
- **ענפים ו-CD:** לכל סביבה ענף משלה: `dev` לסביבת dev, `stage` ל-stage, `main` ל-prod. PRs של פיצ'רים נפתחים מול `dev`; קידום הוא PR מ-`dev` ל-`stage` ומ-`stage` ל-`main`, וממוזג ב-merge commit (לא squash) כדי שלענפים תהיה היסטוריה אחת. כל PR אחר ממוזג ב-squash, וענף מקבל שינויים חדשים במיזוג ענף הבסיס לתוכו, אף פעם לא ב-rebase או force-push. כל דחיפה לענף פורסת לסביבה שלו: dev אוטומטית, stage ו-prod אחרי אישור מאשר, אבל רק אחרי ש-CI ו-Infra עברו על אותו commit: שניהם רצים בתוך Deploy (`workflow_call`) וה-job של הפריסה תלוי בהם. בדיקה אדומה עוצרת את הפריסה, ו-commit שכבר אינו הראש של הענף לא נפרס (ה-commit החדש נפרס במקומו). שלושת הענפים מוגנים (רק PR עם `check` עובר), ו-Terraform יוצר את הענפים ואת ההגנות. ה-job של הפריסה מדולג (לא נכשל) עד ש-Terraform מגדיר משתנה מאגר `POSTLY_DEPLOY_<ENV>`, ה-CI מריץ את כל `npm run check` כ-jobs מקבילים (static, unit, db, design, e2e), ו-job מסכם בשם `check` עובר רק אם כולם עברו; בניית האימג' ובדיקת ה-Terraform ב-PR רצות רק כשהשינוי נוגע בהם. כל ה-actions ב-`deploy.yml` וב-`infra.yml` נעולים לפי SHA.
- **CI:** ב-PR שנוגע בהם בונים את שני ה-targets של האימג' ומריצים את בדיקות האימג' (`scripts/check-image.sh`: לא root, בלי קוד בדיקות או playground, והסטאק המקומי על הסימולטורים) (כל שינוי מחוץ ל-`docs/`, `infra/` וקובצי Markdown בשורש), ובודקים `terraform fmt` ו-`validate` (שינוי תחת `infra/`). בדחיפה ל-dev, stage ו-main רצות בתוך Deploy רק בדיקות ה-Terraform; את בדיקות האימג' מריץ ה-job `image` של Deploy על האימג' שהוא דוחף, כך שבדחיפה בונים פעם אחת. הפריסה רצה בכל דחיפה לענף של הסביבה, אחרי ש-CI ו-Infra עברו על אותו commit (ב-stage וב-prod גם אחרי אישור בסביבת GitHub), דרך Workload Identity Federation; הפעלה ידנית משמשת לחזרה לאימג' קודם (תג `tree-<key>`, SHA של commit ב-dev או כל commit שה-tree שלו נבנה ב-dev), בלי להריץ שוב את הבדיקות ובלי לבנות.
- **בונים פעם אחת, פורסים לכל מקום:** repository אחד ב-Artifact Registry, ‏`postly` בפרויקט של dev (שורש dev יוצר אותו, `module.images`), משותף לשלוש הסביבות; התגים בו לא ניתנים לשינוי, ו-Terraform מסרב למחוק אותו. האימג'ים מתויגים `tree-<key>`: גיבוב של ה-tree של ה-commit בלי `docs/`, `infra/` וקובצי Markdown בשורש (`scripts/image-key.sh`), כך ש-squash merge, merge commit של קידום ו-commit של תיעוד או infra בלבד מקבלים את המפתח של האימג' שכבר נבנה. רק דחיפה ל-dev בונה, ב-job ‏`image` שרץ במקביל ל-CI ורק כשהתג חסר: build-push-action עם ה-cache של GitHub Actions דוחף לפי digest ובלי תג, בדיקות האימג' רצות על אותו אימג', ורק אחריהן מתווספים `tree-<key>` וה-SHA. ב-stage וב-prod אין build, ולחשבון הפריסה שלהם יש רק הרשאת קריאה: קידום פורס את ה-digest ש-dev בנה והריץ, ונכשל אם dev לא בנה את ה-tree הזה. דחיפה של תיעוד בלבד לא בונה, ואם ה-digest כבר רץ בכל השירותים גם לא פורסת. אחרי ההחלה הראשונה של dev מוחקים ידנית את ה-repository הישן `postly-dev`, ולפני ההחלה הראשונה של stage או prod מוסיפים את התג `bootstrap` לאימג' בנוי. ל-stage ול-prod צריך גם `image_registry_project` (הפרויקט של dev).
- **מופע web אחד:** עד שהודעות נכנסות יקבלו נעילה עמידה במסד (פריט 14 בתור), שירות ה-web רץ במופע אחד בלבד.
- **ספקים:** עד WP-41 רק dev (ו-local ו-test) יכולים לרוץ, על הסימולטורים; stage ו-prod מסרבים לעלות עד WP-41.
- **מצב מדומה ב-dev (WP-51):** `POSTLY_PROVIDERS=simulators` מותר רק ב-local, test ו-dev. ב-dev מצב הסימולטורים והמדיה נשמרים ב-Postgres (`SIMULATOR_STORE=postgres`, סכמה `simulator` של המשתמש `app_simulator`, שאין לו גישה לטבלאות העסקים), משותפים ל-web, ל-worker ול-sandbox ושורדים הפעלה מחדש. המודל: Vertex AI בכל סביבה פרוסה (T5), בלי מתג. ל-dev אין סודות של ספקים; סימולטור התשלומים חותם בסוד ה-webhook של ההודעות.
- **ה-sandbox:** שירות ל-dev בלבד (`postly-dev-sandbox`), מ-target נפרד (`sandbox`) באותו `Dockerfile`, שחולק עם אימג' המוצר רק את שלבי התלויות ונפרס רק ל-dev, ובנוי מה-playground: צ'אט שבו האדם משחק את בעל העסק והמאשר (ההודעות נחתמות ונשלחות ל-webhook של web), פיד מדומה של אינסטגרם ופייסבוק, ודף תשלום מדומה עם כפתורי תשלום, כישלון וביטול. כפתור "הרשמה חדשה מהמספר הזה" (בראש הדף, כדי שיופיע גם בטלפון, ועם בקשת אישור) פותח עסק חדש בהרשמה עם המספר של האדם כמאשר: העסק הקודם נשאר במסד הנתונים עם מספר מאשר אחר, והצ'אט מתחיל ריק, בלי ההודעות מהמספר ובלי ההודעות שנשלחו אליו. הפיד מציג רק את הפוסטים בחשבונות שהעסק החדש חיבר. ההודעות של מספרים אחרים לא נמחקות. פתיחת ה-sandbox לא מתחילה מחדש: השיחה הקודמת נשארת עד שלוחצים על הכפתור. אין לו גישה ציבורית: רק החשבונות ב-`sandbox_invokers` יכולים לפנות אליו. אף פעם לא `allUsers`, ולא ב-stage או prod. שתי דרכים להגיע אליו: (1) בדפדפן ובטלפון (`cloud_run_iap`, מופעל כברירת מחדל ב-dev): IAP המובנה של Cloud Run (בלי load balancer ובלי עלות) על כתובת ה-`run.app` של השירות (הפלט `sandbox_url`); נכנסים עם חשבון Google, ורק החשבונות ב-`sandbox_members` (ברירת מחדל: `sandbox_invokers`) עוברים. ה-OAuth client נוצר פעם אחת ב-Cloud console (ראו "כניסה בדפדפן ב-dev" למטה). אז גם קישורי התשלום מצביעים לכתובת הזו. (2) דרך `gcloud run services proxy postly-dev-sandbox --region me-west1 --port 8081` ופותחים `http://localhost:8081` (כש-IAP פעיל ה-proxy עלול לא לעבור; משתמשים בדפדפן). ה-UI משתמש רק בכתובות יחסיות, והוא דוחה `POST` עם `Origin` זר (CSRF).
- **ספקים:** עד WP-41 האימג' רץ רק על הסימולטורים. Gemini רץ דרך Vertex AI עם חשבון השירות: Terraform מפעיל את `aiplatform.googleapis.com` ונותן `roles/aiplatform.user`, ואין סוד של מפתח מודל.
- **Terraform:** מודולים לרשת פרטית, Artifact Registry, חשבונות שירות בהרשאות מינימליות, Secret Manager (שמות בלבד, בלי ערכים), Cloud SQL עם כתובת פרטית בלבד, דלי מדיה פרטי עם מחזור חיים, Cloud Run ל-web ול-worker, וניטור והתראות. שלוש סביבות: dev (זולה, תמיד פעילה, על סימולטורים או חשבונות בדיקה, פריסה חופשית בלי מאשר אבל רק מ-main, מופע אחד, Cloud SQL קטן (`db-g1-small`, כי `db-f1-micro` מאפשר רק כ-25 חיבורים) בלי HA, לוגים נשמרים 7 ימים, וזה חל על כל הפרויקט, לכן ל-dev פרויקט משלו), stage (בדיקה לפני prod על חשבונות בדיקה) ו-prod; Terraform גם מפעיל את ה-APIs, מייצר סיסמאות אקראיות לכל משתמשי המסד, לסוד ה-webhook ולמשתמש ה-postgres (וכותב מהם את כתובת המנהל), יוצר את סביבות GitHub עם המשתנים, ושורש `infra/bootstrap` יוצר דלי state פרטי עם גרסאות. הסודות שנוצרו נמצאים ב-state, וזה מקובל רק כי הדלי פרטי ועם גרסאות.
- **ענפים ו-CD:** לכל סביבה ענף משלה: `dev` לסביבת dev, `stage` ל-stage, `main` ל-prod. PRs של פיצ'רים נפתחים מול `dev`; קידום הוא PR מ-`dev` ל-`stage` ומ-`stage` ל-`main`. כל דחיפה לענף פורסת לסביבה שלו: dev אוטומטית, stage ו-prod אחרי אישור מאשר, אבל רק אחרי ש-CI ו-Infra עברו על אותו commit: שניהם רצים בתוך Deploy (`workflow_call`) וה-job של הפריסה תלוי בהם. בדיקה אדומה עוצרת את הפריסה, ו-commit שכבר אינו הראש של הענף לא נפרס (ה-commit החדש נפרס במקומו). שלושת הענפים מוגנים (רק PR עם `check` עובר), ו-Terraform יוצר את הענפים ואת ההגנות.
- **CI:** בכל PR בונים את האימג', מריצים את הסטאק המקומי על הסימולטורים, ובודקים `terraform fmt` ו-`validate`. הפריסה ידנית בלבד, עם אישור בסביבת GitHub ו-Workload Identity Federation.
- **כמה מופעי web:** רצף הודעות נכנסות עמיד: ההודעות שמורות במסד, המסירה היא נעילה (claim) על השורות, וההתעוררות היא משימת pg-boss בשם `inbound-burst` לפי עסק ושולח. לכן שירות ה-web רשאי לרוץ בכמה מופעים (`web_max_instances` בין 1 ל-10, ברירת מחדל 1); את המספר מעלה האדם ב-Terraform.
- **ספקים:** עד WP-41 האימג' רץ רק על הסימולטורים.
- **מה האדם עושה:** יוצר פרויקט GCP וחיוב, `gcloud auth application-default login`, מגדיר `GITHUB_TOKEN`, מריץ apply ל-bootstrap ואז לסביבה (קובץ משתנים עם שלושה ערכים בלבד), ופורס. אחר כך: חשבונות הספקים (WP-41) והחלטה על כניסה לקונסולה.
- **מיגרציות וחזרה לאחור:** מיגרציה רצה לפני הקוד וחייבת להשאיר את הגרסה הקודמת עובדת. חזרה לאחור בקוד היא החזרת התנועה לגרסה הקודמת; שחזור נתונים הוא שחזור לנקודת זמן למופע חדש.
- **סוד ה-webhook:** ב-dev, ב-stage וב-prod התהליכים מסרבים לעלות בלי סוד webhook מ-Secret Manager, או כשהסוד הוא ברירת המחדל הציבורית של הסימולטור.
- **השער האמיתי לפריסה:** לחשבון הפריסה אין הרשאה ישירה לנתונים, אבל הוא יכול להריץ כל אימג' כמשימת המיגרציה, שיש לה גישת מנהל למסד. לכן השער האמיתי הוא סביבת GitHub: מאשרים נדרשים ב-stage וב-prod, ומדיניות שמתירה לכל סביבה פריסה רק מהענף שלה (`dev`, `stage`, או `main` ל-prod). הפעולות בתהליך הפריסה נעוצות לפי SHA.
- **בלי לוג של פקודות SQL:** הדגל `log_statement` של Cloud SQL חייב להישאר `none`, כי פקודות ALTER ROLE של משימת המיגרציה מכילות את הסיסמאות. Terraform קובע אותו במפורש.
- **לוגים:** כל תהליך כותב שורת JSON אחת לכל אירוע ל-stdout בפורמט של Cloud Logging, עם מזהי בקשה, עסק, הודעה ו-job, בלי תוכן לקוח, טלפונים או סודות. פירוט ב-[observability.summary.he.md](observability.summary.he.md).
- **מדדים, traces ושגיאות (WP-48):** web, worker ו-console שולחים מדדי OpenTelemetry ל-Cloud Monitoring (`workload.googleapis.com/postly.*`) ו-spans ל-Cloud Trace; כל שורת `ERROR` מגיעה ל-Error Reporting. השליחה פעילה רק ב-dev, stage ו-prod. ה-APIs נוספו ב-Terraform; לחשבונות השירות כבר יש הרשאות כתיבת מדדים ו-traces. שמות המדדים וה-labels (בשביל WP-49) ב-observability.md.
- **`POSTLY_ENV` חובה:** תהליך בלי המשתנה לא עולה, כך ששירות פרוס לא נופל בטעות לסוד ה-webhook הציבורי.
- **קודם dev:** אפשר להריץ רק את `infra/bootstrap` ואת `infra/environments/dev`. זה יוצר את ענף `dev`, ההגנה שלו, סביבת GitHub של dev והמשתנים שלה, בלי שום דבר של stage או prod. ההגנה על `main` וענף `stage` נוצרים רק בשורשים של prod ו-stage, ועד אז דחיפות ל-`stage` או ל-`main` מדלגות על הפריסה. השורשים לא חולקים משאבי GitHub, ולכל אחד state בתחילית משלו בדלי `<project>-tfstate` (דלי אחד לכל פרויקט). ה-apply הראשון רץ בשלושה מעברים (Cloud Run לא יוצר שירות מאימג' `bootstrap` שלא קיים); המדריך המלא: [deploy-dev-guide.md](deploy-dev-guide.md).

- לקונסולה חשבון שירות משלה (`postly-<env>-console`) שקורא רק את סיסמאות ההתחברות של תהליך הקונסולה ואת סוד ה-webhook (WP-84).

- תקציב החיבורים ל-Cloud SQL כולל גם את שירות הקונסולה (מופע אחד); `DB_POOL_MAX` נקבע ב-Terraform (WP-87). הקונסולה לא שולחת משימות בפועל, לכן ה-pg-boss שלה עולה רק בשליחה ראשונה (בלי תחזוקה ובלי cron) ובדרך כלל לא מחזיק חיבורים; התקציב עדיין סופר אותם.
## כניסה בדפדפן ב-dev
- ב-dev הקונסולה וה-sandbox נפתחים בדפדפן ובטלפון עם כניסת Google דרך IAP המובנה של Cloud Run על כל שירות (`cloud_run_iap`, מופעל כברירת מחדל ב-dev ואסור ב-stage וב-prod): בלי load balancer, בלי דומיין, בלי עלות ובלי proxy.
- Terraform יוצר הכול חוץ מה-OAuth client: ‏`iap_enabled` על שני השירותים (ה-ingress של הקונסולה נהיה "all"), ‏`iap.httpsResourceAccessor` על כל שירות בלבד ל-`console_members` ול-`sandbox_members` (שתיהן ברירת מחדל `sandbox_invokers`; אף פעם לא `allUsers`), ‏`run.invoker` לסוכן השירות של IAP, ‏`CONSOLE_IAP_AUDIENCE` = ‏`/projects/<מספר>/locations/me-west1/services/postly-dev-console`, ‏`CONSOLE_HOST` = כתובת ה-run.app, והפלטים `console_url` ו-`sandbox_url`.
- צעד ידני אחד, כי ה-client המנוהל של Google מכניס רק משתמשים בתוך ארגון, לפרויקט אין ארגון, ואין API ליצירת OAuth client: ב-Cloud console, ‏Cloud Run ← `postly-dev-sandbox` ← Security ← לסמן Identity-Aware Proxy ← Save ← Edit policy ← Configure in IAP ← Configure consent screen ‏(External, ולהוסיף את ה-Gmail כ-test user) ← Auto generate credentials ← Save. השירות `postly-dev-sandbox` חייב להיות קיים (בפרויקט חדש: apply ראשון, הצעד הזה, ואז apply נוסף). ה-client נשמר בהגדרות ה-IAP של הפרויקט, והסוד שלו לא נכנס ל-Terraform. לפני ה-plan מוחקים מ-`terraform.tfvars` שורות ישנות של `sandbox_iap_client_id`, ‏`console_iap_client_id` או `console_domain`; אם ה-load balancer של הקונסולה או `google_iap_settings` של ה-sandbox הופעלו בעבר, ה-plan מוחק אותם, וזה צפוי. אחר כך plan ו-apply, ופותחים את `console_url` ואת `sandbox_url`.

## כניסה לקונסולה ב-stage וב-prod: צעדים חד-פעמיים (WP-82)
- Terraform בונה את ה-load balancer עם IAP רק כשהמשתנה `console_iap_client_id` מוגדר; לפני כן לא נוצר דבר ולא משלמים.
- ידנית, פעם אחת בכל פרויקט: מסך הסכמה (Branding) מסוג External, ‏OAuth client מסוג Web application עם redirect URI של IAP, הוספת הסוד ל-`postly-<env>-console-iap-client-secret`, ויצירת סוכן השירות של IAP (`gcloud beta services identity create --service=iap.googleapis.com`).
- ב-`terraform.tfvars`: ‏`console_iap_client_id`, ‏`console_members` (ריק כברירת מחדל) ו-`console_domain` (חובה ב-stage וב-prod). אחר כך רשומת `A` לכתובת `console_ip`; התעודה המנוהלת פעילה תוך כשעה.
- משתני סביבה חדשים: `CONSOLE_AUTH`, ‏`CONSOLE_IAP_AUDIENCE`, ‏`CONSOLE_HOST`, ‏`CONSOLE_DEV_ACTOR`.
- `CONSOLE_IAP_AUDIENCE` מקבל אחת משתי צורות: ‏`/projects/<מספר>/global/backendServices/<id>` מאחורי load balancer, או `/projects/<מספר>/locations/<אזור>/services/<שירות>` עם IAP המובנה של Cloud Run.
- עלות: כ-18 דולר בחודש לכל סביבה עם load balancer; ב-dev אפס.
- **Gemini אמיתי והסוכנת ב-dev:** כל סביבה פרוסה רצה תמיד על Gemini דרך Vertex AI וכל הזרימות של הסוכנת תמיד פועלות, בלי משתנים `models` ו-`agent_flows` ובלי `POSTLY_MODELS` ו-`POSTLY_AGENT_FLOWS` (6.11.2026). **יש למחוק את השורות `models` ו-`agent_flows` מ-`terraform.tfvars` של dev לפני ה-plan הבא.** משתני dev שנשארו: `vertex_location` (ברירת מחדל `eu`, האזור המרובה של האיחוד האירופי, כי Vertex לא מגיש Gemini מ-`me-west1` ו-Gemini 3.5 Flash-Lite לא זמין באזורים בודדים כמו `europe-west4`; קובץ tfvars שעדיין קובע `europe-west4` צריך להסיר את השורה), ו-`billing_account` שמוסיף תקציב חודשי ב-Cloud Billing על Vertex AI בפרויקט, `model_budget_usd` (50 דולר ב-dev, פי שניים מברירת המחדל 25, באישור הבעלים), עם מיילים ב-50%, 90% ו-100%. התקציב רק מתריע; מה שעוצר הוצאה הן התקרות היומיות של הסוכנת. ה-API והרשאת `roles/aiplatform.user` כבר קיימים, רק לחשבונות של web ו-worker. בסנדבוקס, אחרי "הרשמה חדשה מהמספר הזה", ההרשמה רצה עם הסוכנת.
- **חלון ההפצה של מיגרציה 0024:** המיגרציה מוחקת את עמודות `agent_flows` באותה גרסה שמפסיקה לקרוא אותן (חריגה מ"להרחיב ואז לצמצם"). בזמן שבין ריצת המיגרציה לעליית הגרסה החדשה, הגרסה הקודמת ב-dev עדיין קוראת את העמודה והשאילתות שלה נכשלות. זה לא מזיק: ב-dev יש רק נתוני בדיקה, הודעה שנכשלה משתחררת ונמסרת שוב לגרסה החדשה, ו-stage ו-prod מעולם לא הריצו גרסה שקוראת את העמודות. מחיקות עתידיות חוזרות ל"להרחיב ואז לצמצם".
