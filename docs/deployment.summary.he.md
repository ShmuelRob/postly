# פריסה: עיקרי הדברים

תקציר של [deployment.md](deployment.md). שום דבר עוד לא נפרס: סוכנים כותבים ומאמתים את הקוד בלבד, ויצירת משאבים בענן, הוצאת כסף ופריסה ממתינים לאדם (נקודת אישור H8).

- **אימג' אחד:** Node 26 עם Chromium של Playwright ו-sharp, רץ כמשתמש שאינו root. הפקודה בוחרת תהליך: `web` (Fastify, ה-webhooks), `worker` (pg-boss) או `migrate` (משימת המיגרציה). קוד הבדיקות וה-playground לא נכנסים לאימג'.
- **ה-worker:** מריץ את `WeeklyUpdates.tick` כל שעה עגולה, בתור pg-boss במדיניות singleton, כך שגם עם כמה מופעים רץ רק tick אחד בכל רגע.
- **משימת המיגרציה:** מריצה את המיגרציות (שיוצרות משתמש מסד נתונים לכל תפקיד), קובעת את הסיסמאות מ-Secret Manager, ויוצרת משתמש נפרד ל-pg-boss. Terraform לא יוצר תפקידים במסד.
- **Terraform:** מודולים לרשת פרטית, Artifact Registry, חשבונות שירות בהרשאות מינימליות, Secret Manager (שמות בלבד, בלי ערכים), Cloud SQL עם כתובת פרטית בלבד, דלי מדיה פרטי עם מחזור חיים, Cloud Run ל-web ול-worker, וניטור והתראות. שלוש סביבות: dev (זולה, תמיד פעילה, על סימולטורים או חשבונות בדיקה, פריסה חופשית בלי מאשר אבל רק מ-main, מופע אחד, Cloud SQL קטן (`db-g1-small`, כי `db-f1-micro` מאפשר רק כ-25 חיבורים) בלי HA, לוגים נשמרים 7 ימים, וזה חל על כל הפרויקט, לכן ל-dev פרויקט משלו), stage (בדיקה לפני prod על חשבונות בדיקה) ו-prod; Terraform גם מפעיל את ה-APIs, מייצר סיסמאות אקראיות לכל משתמשי המסד, לסוד ה-webhook ולמשתמש ה-postgres (וכותב מהם את כתובת המנהל), יוצר את סביבות GitHub עם המשתנים, ושורש `infra/bootstrap` יוצר דלי state פרטי עם גרסאות. הסודות שנוצרו נמצאים ב-state, וזה מקובל רק כי הדלי פרטי ועם גרסאות.
- **ענפים ו-CD:** לכל סביבה ענף משלה: `dev` לסביבת dev, `stage` ל-stage, `main` ל-prod. PRs של פיצ'רים נפתחים מול `dev`; קידום הוא PR מ-`dev` ל-`stage` ומ-`stage` ל-`main`. כל דחיפה לענף פורסת לסביבה שלו: dev אוטומטית, stage ו-prod אחרי אישור מאשר. שלושת הענפים מוגנים (רק PR עם `check` עובר), ו-Terraform יוצר את הענפים ואת ההגנות.
- **CI:** בכל PR בונים את האימג', מריצים את הסטאק המקומי על הסימולטורים, ובודקים `terraform fmt` ו-`validate`. הפריסה ידנית בלבד, עם אישור בסביבת GitHub ו-Workload Identity Federation.
- **מופע web אחד:** עד שהודעות נכנסות יקבלו נעילה עמידה במסד (פריט 14 בתור), שירות ה-web רץ במופע אחד בלבד.
- **ספקים:** עד WP-41 רק dev (ו-local ו-test) יכולים לרוץ, על הסימולטורים; stage ו-prod מסרבים לעלות עד WP-41.
- **מצב מדומה ב-dev (WP-51):** `POSTLY_PROVIDERS=simulators` מותר רק ב-local, test ו-dev. ב-dev מצב הסימולטורים והמדיה נשמרים ב-Postgres (`SIMULATOR_STORE=postgres`, סכמה `simulator` של המשתמש `app_simulator`, שאין לו גישה לטבלאות העסקים), משותפים ל-web, ל-worker ול-sandbox ושורדים הפעלה מחדש. המודל: `POSTLY_MODELS=vertex` (T5) או `simulator`. ל-dev אין סודות של ספקים; סימולטור התשלומים חותם בסוד ה-webhook של ההודעות.
- **ה-sandbox:** שירות ל-dev בלבד (`postly-dev-sandbox`), מאימג' נפרד (`Dockerfile.sandbox`) שלא נבנה ל-stage ול-prod, ובנוי מה-playground: צ'אט שבו האדם משחק את בעל העסק והמאשר (ההודעות נחתמות ונשלחות ל-webhook של web), פיד מדומה של אינסטגרם ופייסבוק, ודף תשלום מדומה עם כפתורי תשלום, כישלון וביטול. אין לו גישה ציבורית: רק החשבונות ב-`sandbox_invokers` יכולים לפנות אליו. מגיעים אליו עם `gcloud run services proxy postly-dev-sandbox --region me-west1 --port 8081` ופותחים `http://localhost:8081`.
- **מה האדם עושה:** יוצר פרויקט GCP וחיוב, `gcloud auth application-default login`, מגדיר `GITHUB_TOKEN`, מריץ apply ל-bootstrap ואז לסביבה (קובץ משתנים עם שלושה ערכים בלבד), ופורס. אחר כך: חשבונות הספקים (WP-41) והחלטה על כניסה לקונסולה.
- **מיגרציות וחזרה לאחור:** מיגרציה רצה לפני הקוד וחייבת להשאיר את הגרסה הקודמת עובדת. חזרה לאחור בקוד היא החזרת התנועה לגרסה הקודמת; שחזור נתונים הוא שחזור לנקודת זמן למופע חדש.
- **סוד ה-webhook:** ב-dev, ב-stage וב-prod התהליכים מסרבים לעלות בלי סוד webhook מ-Secret Manager, או כשהסוד הוא ברירת המחדל הציבורית של הסימולטור.
- **השער האמיתי לפריסה:** לחשבון הפריסה אין הרשאה ישירה לנתונים, אבל הוא יכול להריץ כל אימג' כמשימת המיגרציה, שיש לה גישת מנהל למסד. לכן השער האמיתי הוא סביבת GitHub: מאשרים נדרשים ב-stage וב-prod, ומדיניות שמתירה פריסה רק מ-main. הפעולות בתהליך הפריסה נעוצות לפי SHA.
- **בלי לוג של פקודות SQL:** הדגל `log_statement` של Cloud SQL חייב להישאר `none`, כי פקודות ALTER ROLE של משימת המיגרציה מכילות את הסיסמאות. Terraform קובע אותו במפורש.
- **`POSTLY_ENV` חובה:** תהליך בלי המשתנה לא עולה, כך ששירות פרוס לא נופל בטעות לסוד ה-webhook הציבורי.
