# פריסה: עיקרי הדברים

תקציר של [deployment.md](deployment.md). שום דבר עוד לא נפרס: סוכנים כותבים ומאמתים את הקוד בלבד, ויצירת משאבים בענן, הוצאת כסף ופריסה ממתינים לאדם (נקודת אישור H8).

- **אימג' אחד:** Node 26 עם Chromium של Playwright ו-sharp, רץ כמשתמש שאינו root. הפקודה בוחרת תהליך: `web` (Fastify, ה-webhooks), `worker` (pg-boss), `console` (הקונסולה הפנימית, שירות נפרד עם ingress פנימי בלבד ובלי גישה ציבורית, ראו [security.summary.he.md](security.summary.he.md)) או `migrate` (משימת המיגרציה). קוד הבדיקות וה-playground לא נכנסים לאימג'.
- **ה-worker:** מריץ את `WeeklyUpdates.tick` כל שעה עגולה, בתור pg-boss במדיניות singleton, כך שגם עם כמה מופעים רץ רק tick אחד בכל רגע.
- **משימת המיגרציה:** מריצה את המיגרציות (שיוצרות משתמש מסד נתונים לכל תפקיד), קובעת את הסיסמאות מ-Secret Manager, ויוצרת משתמש נפרד ל-pg-boss. Terraform לא יוצר תפקידים במסד.
- **Terraform:** מודולים לרשת פרטית, Artifact Registry, חשבונות שירות בהרשאות מינימליות, Secret Manager (שמות בלבד, בלי ערכים), Cloud SQL עם כתובת פרטית בלבד, דלי מדיה פרטי עם מחזור חיים, Cloud Run ל-web ול-worker, וניטור והתראות. שלוש סביבות: dev (זולה, תמיד פעילה, על סימולטורים או חשבונות בדיקה, פריסה אוטומטית בלי מאשר מענף `dev`, מופע אחד, אותם גדלים כמו stage ו-prod, לוגים נשמרים 7 ימים, וזה חל על כל הפרויקט, לכן ל-dev פרויקט משלו), stage (בדיקה לפני prod על חשבונות בדיקה) ו-prod; Terraform גם מפעיל את ה-APIs, מייצר סיסמאות אקראיות לכל משתמשי המסד, לסוד ה-webhook ולמשתמש ה-postgres (וכותב מהם את כתובת המנהל), יוצר את סביבות GitHub עם המשתנים, ושורש `infra/bootstrap` יוצר דלי state פרטי עם גרסאות. הסודות שנוצרו נמצאים ב-state, וזה מקובל רק כי הדלי פרטי ועם גרסאות.
- **גדלים (פריטים 21, 23 בתור):** כל הסביבות בגודל בינוני-נמוך באזור `me-west1` (תל אביב), בלי רפליקות ובלי HA: Cloud SQL `db-custom-2-7680` (2 vCPU, 7.5GB, `max_connections` 400), web עם 1 vCPU ו-2GiB (מופע אחד), worker עם 2 vCPU ו-4GiB (עד מופע אחד, ב-prod עד שניים). הגדלים בתוך המגבלות של GCP (ב-Cloud Run מעל 4GiB צריך לפחות 2 vCPU; ב-Cloud SQL בין 0.9 ל-6.5GB לכל vCPU). Terraform בודק שסך החיבורים (55 לכל תהליך: 15 משתמשים כפול 3, ועוד 10 של pg-boss, ועוד job ההגירה ומרווח) לא עובר את `max_connections`.
- **מחזור חיים של המדיה:** גיל המעבר ל-Coldline ארוך מתקופת השמירה של 30 יום אחרי ביטול: מעבר ל-Coldline אחרי 180 יום. גרסאות ישנות (כולל קבצים שנמחקו) נמחקות אחרי 7 ימים, כך שמדיה שנמחקה ביום 30 נעלמת עד יום 37 בערך. רק קבצים זמניים ב-`tmp/` נמחקים אחרי יום.
- **מי ממזג ומי מאשר פריסה (מקובל כרגע):** כל הסוכנים מריצים `gh` כחשבון של האדם, שהוא המאשר היחיד ומנהל המאגר, כך ש-GitHub לבד לא מונע מסוכן לאשר פריסה. הכלל: רק סשן הסוקר ממזג PRs, כולל PRs של קידום (`dev` ל-`stage`, `stage` ל-`main`); שאר הסוכנים רק פותחים PRs. אף סוכן לא מאשר פריסה ל-stage או ל-prod, רק האדם. בהמשך אפשר לחזק עם זהות GitHub נפרדת לסוכנים בלי הרשאות ניהול או אישור.
- **ענפים ו-CD:** לכל סביבה ענף משלה: `dev` לסביבת dev, `stage` ל-stage, `main` ל-prod. PRs של פיצ'רים נפתחים מול `dev`; קידום הוא PR מ-`dev` ל-`stage` ומ-`stage` ל-`main`, וממוזג ב-merge commit (לא squash) כדי שלענפים תהיה היסטוריה אחת. כל PR אחר ממוזג ב-squash, וענף מקבל שינויים חדשים במיזוג ענף הבסיס לתוכו, אף פעם לא ב-rebase או force-push. כל דחיפה לענף פורסת לסביבה שלו: dev אוטומטית, stage ו-prod אחרי אישור מאשר. שלושת הענפים מוגנים (רק PR עם `check` עובר), ו-Terraform יוצר את הענפים ואת ההגנות. ה-job של הפריסה מדולג (לא נכשל) עד ש-Terraform מגדיר משתנה מאגר `POSTLY_DEPLOY_<ENV>`, ה-CI מריץ את כל `npm run check` כ-jobs מקבילים (static, unit, db, design, e2e), ו-job מסכם בשם `check` עובר רק אם כולם עברו; בניית האימג' ובדיקת ה-Terraform ב-PR רצות רק כשהשינוי נוגע בהם. כל ה-actions ב-`deploy.yml` וב-`infra.yml` נעולים לפי SHA.
- **CI:** בכל דחיפה ל-dev, stage ו-main, וב-PR שנוגע בהם, בונים את האימג' ומריצים את הסטאק המקומי על הסימולטורים (כל שינוי מחוץ ל-`docs/`, `infra/` וקובצי Markdown בשורש), ובודקים `terraform fmt` ו-`validate` (שינוי תחת `infra/`). הפריסה רצה בכל דחיפה לענף של הסביבה (ב-stage וב-prod אחרי אישור בסביבת GitHub), דרך Workload Identity Federation; הפעלה ידנית משמשת לחזרה לאימג' קודם.
- **מופע web אחד:** עד שהודעות נכנסות יקבלו נעילה עמידה במסד (פריט 14 בתור), שירות ה-web רץ במופע אחד בלבד.
- **ספקים:** עד WP-41 האימג' רץ רק על הסימולטורים. Gemini רץ דרך Vertex AI עם חשבון השירות: Terraform מפעיל את `aiplatform.googleapis.com` ונותן `roles/aiplatform.user`, ואין סוד של מפתח מודל.
- **מה האדם עושה:** יוצר פרויקט GCP וחיוב, `gcloud auth application-default login`, מגדיר `GITHUB_TOKEN`, מריץ apply ל-bootstrap ואז לסביבה (קובץ משתנים עם שלושה ערכים בלבד), ופורס. אחר כך: חשבונות הספקים (WP-41) והחלטה על כניסה לקונסולה.
- **מיגרציות וחזרה לאחור:** מיגרציה רצה לפני הקוד וחייבת להשאיר את הגרסה הקודמת עובדת. חזרה לאחור בקוד היא החזרת התנועה לגרסה הקודמת; שחזור נתונים הוא שחזור לנקודת זמן למופע חדש.
- **סוד ה-webhook:** ב-dev, ב-stage וב-prod התהליכים מסרבים לעלות בלי סוד webhook מ-Secret Manager, או כשהסוד הוא ברירת המחדל הציבורית של הסימולטור.
- **השער האמיתי לפריסה:** לחשבון הפריסה אין הרשאה ישירה לנתונים, אבל הוא יכול להריץ כל אימג' כמשימת המיגרציה, שיש לה גישת מנהל למסד. לכן השער האמיתי הוא סביבת GitHub: מאשרים נדרשים ב-stage וב-prod, ומדיניות שמתירה לכל סביבה פריסה רק מהענף שלה (`dev`, `stage`, או `main` ל-prod). הפעולות בתהליך הפריסה נעוצות לפי SHA.
- **בלי לוג של פקודות SQL:** הדגל `log_statement` של Cloud SQL חייב להישאר `none`, כי פקודות ALTER ROLE של משימת המיגרציה מכילות את הסיסמאות. Terraform קובע אותו במפורש.
- **`POSTLY_ENV` חובה:** תהליך בלי המשתנה לא עולה, כך ששירות פרוס לא נופל בטעות לסוד ה-webhook הציבורי.
- **קודם dev:** אפשר להריץ רק את `infra/bootstrap` ואת `infra/environments/dev`. זה יוצר את ענף `dev`, ההגנה שלו, סביבת GitHub של dev והמשתנים שלה, בלי שום דבר של stage או prod. ההגנה על `main` וענף `stage` נוצרים רק בשורשים של prod ו-stage, ועד אז דחיפות ל-`stage` או ל-`main` מדלגות על הפריסה. השורשים לא חולקים משאבי GitHub, ולכל אחד state בתחילית משלו בדלי `<project>-tfstate` (דלי אחד לכל פרויקט). הפקודות המדויקות ב-deployment.md.
